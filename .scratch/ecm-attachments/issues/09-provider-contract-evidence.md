## Question

รวบรวมหลักฐานจากเจ้าของ ECM หรือ sandbox ที่ได้รับอนุญาต สำหรับข้อที่เอกสารและ source ไม่พอจะยืนยัน เพื่อให้เลือกวิธีจัดเก็บ ตั้งชื่อ และแทนที่ไฟล์โดยไม่ทำประวัติเสียหายได้ งานนี้เป็นการจัดหาข้อเท็จจริง ไม่ใช่การเลือกดีไซน์แทนผู้ใช้

ขอคำตอบหรือผลทดสอบที่ทำซ้ำได้ตามรายการต่อไปนี้:

- อัปโหลดชื่อและปลายทางเดิมซ้ำแล้วสร้างไฟล์ใหม่ เขียนทับไฟล์เดิม เป็น version หรือปฏิเสธ? ตัวระบุ/ลิงก์เดิมยังอ่าน bytes เดิมได้หรือไม่?
- วิธีตรวจผลเมื่อผู้ให้บริการรับไฟล์แล้วแต่ผู้เรียกไม่ได้รับคำตอบ วิธีแยกไฟล์ที่เพิ่งสร้างจากไฟล์ของคนอื่น และขอบเขตของการลบด้วย file token
- รูปแบบ response จริงของการอัปโหลด รวม single/multiple file และตัวระบุที่ใช้ตรวจหรือดึงไฟล์ภายหลัง
- มี API สำหรับโครงสร้างปีงบประมาณ/โฟลเดอร์และสิทธิ์เลือกปลายทางอย่างไร นอกเหนือจากหมวดและ path ที่เอกสารแสดง? ใครเป็นผู้สร้างโครงสร้างที่ยังไม่มี?
- ขีดจำกัดขนาดไฟล์และชื่อไฟล์ ข้อจำกัดของไฟล์เข้ารหัส และเงื่อนไขที่ต้องทราบก่อนตั้งเกณฑ์รับไฟล์ตามขอบเขตล่าสุด
- การ login ใหม่กระทบ token ของคำขอเดิมหรือบริการอื่นที่ใช้บัญชีเดียวกันอย่างไร? บัญชี Folio ควรแยกสิทธิ์และ credential จากบริการอื่นอย่างไรตามข้อกำหนดผู้ให้บริการ?
- `file_link` ต้องผ่านสิทธิ์ใด หมดอายุหรือเปลี่ยนได้หรือไม่ และมีวิธีอ่านไฟล์ด้วย identity ที่ชี้ bytes เดิมโดยไม่ค้นหา latest อย่างไร?

เริ่มจากคำยืนยันของเจ้าของบริการพร้อมเอกสารหรือ contract ตัวอย่างที่ลบข้อมูลลับแล้ว หากจำเป็นต้องทดสอบจริง ต้องมี sandbox/บัญชีทดสอบ/โฟลเดอร์ทดสอบและขอบเขตที่อนุญาตชัดเจนก่อน ห้ามใช้ข้อมูลจริงเพื่อทดสอบ overwrite/delete และห้ามพิมพ์ค่า credentials ลง ticket

### Clarification — 2026-11-12 — ผลชี้แจงจากผู้ใช้

- ชื่อไฟล์ซ้ำ: ยังเป็นการคาดการณ์ว่าเขียนทับ ไม่ได้ยืนยันจากเจ้าของ DCM
- การลบ: ลบไฟล์ได้ แต่กู้คืนหลังลบไม่ได้
- ตาราง `status/data: Null/msg` เป็น response ของ Delete ไม่ใช่ Upload; ยังไม่มีตัวอย่างผล Upload สำเร็จ
- บัญชีบริการ: ต้องใช้บัญชี ECM ร่วมกัน ไม่สามารถวางแผนบนสมมติฐานว่าจะมีบัญชีแยกสำหรับ Folio
- โฟลเดอร์กับ Document Category: ยังไม่ทราบความสัมพันธ์

ขอหลักฐานเพิ่มเฉพาะส่วนที่ยังไม่ทราบ:

1. พฤติกรรมเมื่ออัปโหลดชื่อและปลายทางเดิมซ้ำ รวมผลต่อ bytes/token/link เดิม และมีวิธีเรียกไฟล์ฉบับเก่าหรือไม่
2. ตัวอย่าง response ของ Upload สำเร็จและตัวระบุไฟล์ที่ใช้ภายหลัง โดยปิด token, URL และข้อมูลจริง
3. วิธีแจกแจงและระบุโฟลเดอร์ที่ PM สร้าง ความสัมพันธ์กับ Document Category และค่าที่ต้องส่งในโหมดระบุปี/เลขหนังสือ/ปลายทาง

ขนาด PDF ยังบันทึกเป็น “ประมาณ 10mb” ไม่แปลงเป็น hard limit หรืออ้างว่าได้ทดสอบขอบเขตแล้ว การตรวจผ่านหน้า DCM โดย PM เป็นแนวทางที่แจ้งว่ามีอยู่ ไม่ใช่ API ยืนยันผลอัปโหลดอัตโนมัติ

แยกคำถามที่ชัดแล้วไปยัง [การใช้บัญชี ECM ร่วมโดยไม่ตัด token ของระบบอื่น](10-shared-ecm-login.md) เพื่อหารือเจ้าของการ login; ข้อเท็จจริงที่ต้องใช้เริ่มคำถามนั้นได้รับแล้ว จึงไม่ต้องรอเรื่องชื่อซ้ำหรือโฟลเดอร์ ส่วนงานนี้ยัง claimed และรอหลักฐานข้างต้น ไม่เพิ่มรายการใน Decisions so far

### Clarification — 2026-11-12 — ยืนยันการเขียนทับและขอบเขตเอกสารที่มี

- ผู้ใช้ยืนยันว่าไฟล์ชื่อซ้ำเขียนทับ และอ่านฉบับเก่าไม่ได้ ข้อนี้แทนที่สถานะ “ยังเป็นการคาดการณ์” ในบันทึกก่อนหน้า ไม่ต้องขอให้ยืนยันเรื่องเดิมซ้ำ
- ไม่มีตัวอย่าง response จากการอัปโหลดจริง มีเพียง API docs ภาพที่ผู้ใช้แนบเป็นหน้า `DELETE /api/beeecm/public/file?token={{ file token }}` ซึ่งระบุ `data: Null`; ไม่ใช่หลักฐาน response ของ Upload
- สำหรับการวางแผนให้อ้างสัญญา Upload จากเอกสารที่วิจัยไว้ โดยยังแยกชัดว่าไม่ได้ตรวจ response ของบริการจริง และมีความต่างกับ schema ของ Ongoing ไม่ขอตัวอย่างที่ผู้ใช้ระบุว่าไม่มีซ้ำ และไม่สร้างผลทดสอบสมมติ
- ผู้ใช้ขอให้ขยายความเรื่องโฟลเดอร์กับ Document Category จึงยังไม่มีคำตอบใหม่ในประเด็นนั้น

ประเด็นโฟลเดอร์ที่ต้องชี้แจง: เอกสาร Upload มี `documentYear`, `documentNumber`, `documentCategory` แต่ยังไม่ระบุว่า category ที่เลือกแทนโฟลเดอร์จริงใด และจะได้รายการปลายทางที่ PM สร้างจากไหน ต้องแยกระหว่าง “เลือกหมวดแล้ว DCM จัดปลายทางตามกฎ” กับ “เลือกโฟลเดอร์จริงที่ PM สร้างได้โดยตรง” ตัวอย่างชื่อหรือ path ที่ใช้ประกอบคำอธิบายเป็นเพียงตัวอย่างสมมติ ไม่ใช่โครงสร้างที่ยืนยันแล้ว

ผลต่อการตัดสินใจตั้งชื่อและวงจรไฟล์: ห้ามพึ่งการอัปโหลดทับไฟล์เดิมเพื่อเก็บประวัติ เพราะฉบับเก่าอ่านไม่ได้ การอัปโหลดก่อนลบอย่างเดียวไม่แก้ความเสี่ยงนี้ ต้องตัดสินวิธีแยกไฟล์ที่ประวัติยังอ้างถึงใน [แหล่งเลขที่หนังสือยืนยันและกติกาชื่อไฟล์](04-confirmation-filename.md) และ [วงจรไฟล์ร่างและการบันทึกโดยไม่สูญหาย](05-safe-draft-lifecycle.md) โดยยังไม่เลือกวิธีแทนผู้ใช้

งานยัง claimed ไม่ใช่ resolved; รอชี้แจงความสัมพันธ์โฟลเดอร์/หมวด ส่วนการตรวจ response จริงยังระบุเป็นข้อจำกัดของหลักฐาน ไม่อ้างว่าได้ทดลองแล้ว

### Resolution — 2026-11-12 — pyw1tt / คำชี้แจงสัญญาและขอบเขตจากผู้ใช้

ปิดงานรวบรวมข้อเท็จจริงสำหรับการวางแผนจากคำตอบของผู้ใช้และ API docs ไม่ใช่การรับรอง deployment หรือผลทดลองจริง ข้อกำหนดใน resolution นี้เป็นฉบับล่าสุด และแทนที่ความไม่แน่ใจเรื่องแหล่งรายการปลายทาง/ค่าที่ส่ง และขอบเขต PDF-only ในบันทึกก่อนหน้า

#### รายการปลายทางและผู้ควบคุม

- ใช้ `GET /api/beeecm/public/document/category` ดึงรายการ Document Category ให้ Admin เลือกว่าปุ่ม upload แต่ละปุ่มจะใช้ category ใด
- สำหรับขอบเขตนี้ ตัวเลือกปลายทางคือ Document Category ไม่ใช่การเพิ่ม browser สำหรับเลือก path หรือโฟลเดอร์ย่อยอิสระทุกชนิดใน DCM
- PM เป็นผู้สร้างโฟลเดอร์ใน DCM; การให้ Folio สร้างโฟลเดอร์เองไม่ได้อยู่ในสัญญาที่ผู้ใช้ระบุ
- ปีงบประมาณที่ส่งมาจากค่า tag `fiscal_year` ไม่ได้สมมติว่าเป็นค่าตั้งปลายทางแยกต่างหาก ใครกำหนด/แก้ไขค่า tag และค่าเดียวกันใช้ทั้ง Response หรือแต่ละแถวยังเป็นคำถามในงานตั้งค่า

#### สัญญาอัปโหลดที่ใช้วางแผน

ใช้ `POST /api/beeecm/public/file` พร้อม Bearer token ของ ECM และ `multipart/form-data` ไม่ใช่ JSON ที่ส่งชื่อไฟล์แทนเนื้อหา:

| Field | แหล่งค่า |
| --- | --- |
| `documentFile` | ไฟล์จริง โดยกำหนด multipart filename ใหม่จากค่า `docs_number` กับชื่อ Document Category ที่ Admin เลือก คงเนื้อหาและนามสกุลเดิมถ้ามี ไม่เปลี่ยนทุกไฟล์ให้เป็น `.pdf` |
| `template` | `0` ซึ่งส่งเป็นข้อความ `"0"` ใน multipart; ไม่ใช้โหมดตั้งปลายทางจาก template ชื่อไฟล์ |
| `documentYear` | ค่า tag `fiscal_year` ของคำตอบชุดที่จะบันทึกหรือส่ง |
| `documentNumber` | ค่า tag `docs_number` ของคำตอบชุดเดียวกัน |
| `documentCategory` | ค่าหมวดที่ Admin เลือกจากรายการ API ไม่ใช่การเลือกโดยผู้กรอก ไม่ส่ง response ทั้งก้อนเป็นค่าฟิลด์นี้ |

ตาม [ผลวิจัย ECM API สำหรับไฟล์แนบ Excel ของ Folio](https://github.com/AquilaStudio2/folio-forms/blob/4098cb7/.scratch/ecm-attachments/research/ecm-api.md) รายการหมวดในเอกสารมี `id` และ `type`; Upload รับ `documentCategory` เป็นชื่อหมวดแบบ string ตัวเลือกจึงใช้ชื่อหมวด `type` ใน payload/ชื่อไฟล์ ไม่แปลงเป็น numeric ID โดยไม่มีหลักฐาน

การบอกว่าต้องยืนยันตัวตนก่อนอัปโหลดไม่ได้หมายความว่าต้อง login ใหม่ทุกครั้งที่ Save/Submit การใช้บัญชีร่วมและการต่ออายุ token ต้องได้ข้อสรุปจาก [การใช้บัญชี ECM ร่วมโดยไม่ตัด token ของระบบอื่น](10-shared-ecm-login.md)

#### ขอบเขตไฟล์และข้อเท็จจริงด้านความปลอดภัย

- ผู้ใช้ขยายจาก PDF-only เป็นไฟล์ทุกชนิด ยังคงหนึ่งไฟล์ต่อช่อง การเลือกไฟล์ยังไม่อัปโหลด; เริ่มเมื่อ User กด Save Draft หรือ Submit
- ชื่อซ้ำเขียนทับไฟล์เดิมและอ่านฉบับเก่าไม่ได้; ลบไฟล์ได้แต่กู้คืนไม่ได้
- URL ของไฟล์เป็น public ไม่ต้องยืนยันตัวตนและไม่มีวันหมดอายุ สิทธิ์ใน Folio ไม่ทำให้ URL ต้นทางเป็น private
- Login ใหม่ทำให้ token เก่าใช้ไม่ได้ และต้องใช้บัญชีร่วมกับระบบอื่น
- กรณีไม่ทราบผลอัปโหลด ผู้ใช้ระบุว่าปัจจุบัน PM ตรวจผ่านหน้า DCM ไม่ได้มีหลักฐาน API สำหรับยืนยันผลหรือ idempotency

#### สิ่งที่ส่งต่อให้ตัดสินใจ ไม่ใช่ข้อรับรองจากงานนี้

- [ระดับการตั้งค่าปลายทางไฟล์ของ Admin](03-admin-storage-policy.md): category ต่อปุ่ม, การใช้ค่าร่วมในแถวตาราง, ผู้ควบคุม `fiscal_year`, ความครบถ้วนก่อนเผยแพร่ และผลของการเปลี่ยนการตั้งค่า
- [แหล่งเลขที่หนังสือยืนยันและกติกาชื่อไฟล์](04-confirmation-filename.md): แหล่งเลขคือ tag `docs_number` แล้ว แต่ขอบเขต scalar/รายแถว ค่าว่าง การเปลี่ยนค่า อักขระ และการป้องกันชื่อชนยังไม่ตัดสิน
- การใช้เพียง `docs_number` กับ category อาจให้ชื่อซ้ำ จึงยังไม่รับรองประวัติ ต้องตกลงวิธีแยกไฟล์เดิมออกจากไฟล์ใหม่ ห้ามเติมรหัสท้ายชื่อหรือเพิ่มที่เก็บสำรองโดยถือว่าผู้ใช้อนุมัติแล้ว
- [ข้อกำหนดชนิดไฟล์และขนาดที่รับได้](07-pdf-acceptance.md): คำตอบเดิม “ประมาณ 10mb” ยังไม่ใช่ขีดจำกัดที่ทดลองแล้ว; ขอบเขตไฟล์ทุกชนิดเป็นความต้องการ ไม่ใช่ผลพิสูจน์ว่าผู้ให้บริการรับทุกชนิด/ทุกขนาด
- ไม่มีตัวอย่าง Upload response จริง ใช้เอกสาร Upload เป็นฐานที่ระบุระดับหลักฐานชัดเจน; `data: Null` ในภาพเป็นของ Delete ไม่ใช้แทน Upload และไม่ปรับ parser ให้รับรูปร่างที่เดาเพื่อกลบความต่างกับ Ongoing

ไม่ได้ login/upload/delete กับ ECM จริง ไม่แก้ application, credentials หรือ DB ไม่อนุมัติการเปลี่ยน Ongoing และไม่ปิด decision tickets อื่นแทนผู้ใช้

### Contract amendment — 2026-11-12 — เก็บ URL และ file token ใน JSON คำตอบ

ผู้ใช้ระบุเพิ่มเติมให้เก็บ URL และ file token จาก response ของการ upload รวมใน JSON ที่เก็บข้อมูลส่วนอื่นของคำตอบ ไม่เก็บไว้เฉพาะใน browser หรือแยก metadata ไปไว้ที่อื่นจน JSON คำตอบไม่มีสองค่านี้

- แหล่งข้อมูลคือ `file_link` และ `file_token` ของไฟล์ที่ upload จริงตามเอกสาร API เก็บความสัมพันธ์กับช่อง/แถวของ tag และ snapshot คำตอบที่ถูกต้อง ไม่จับคู่ URL ของไฟล์หนึ่งกับ token ของอีกไฟล์
- เก็บข้อมูลใน Draft และ snapshot ของแต่ละ Submission/Correction ที่เกี่ยวข้อง การเปลี่ยนไฟล์สร้างคู่ URL/token ใหม่ของฉบับใหม่ ไม่เขียนทับคู่ข้อมูลในประวัติเดิม
- `file_token` ใช้ระบุไฟล์สำหรับ Delete ไม่ใช่ ECM login token; ECM credentials/Bearer token ห้ามอยู่ใน answer JSON หรือเอกสาร export
- การลบต้องใช้ `file_token` จากข้อมูล canonical ที่ server บันทึกไว้ ตรวจสิทธิ์เจ้าของคำตอบ/ช่อง/แถวและการอ้างอิงในประวัติ ไม่เชื่อ token หรือ URL ที่ client ส่งมาให้ลบโดยตรงเพียงเพราะอยู่ใน JSON
- ฝั่งผู้ใช้แสดง URL ไม่แสดง file token เป็นช่องที่แก้ไขได้ ต้องตรวจ schema และ URL จาก upstream ก่อนบันทึก/สร้างลิงก์ ไม่เปิด `javascript:` หรือ scheme ที่ใช้รันเนื้อหาเป็น URL ไฟล์

การวางรูปแบบ JSON และการแปลงค่าไปมาระหว่างเอกสาร Excel กับ metadata เป็นของ [สัญญา JSON ของไฟล์แนบและ URL ใน Excel](11-attachment-json-contract.md) ไม่ได้เลือกรูปแบบ object/metadata key โดยไม่ตรวจ contract เดิม และไม่มี Upload response จริงหรือผล runtime ใหม่จากข้อกำหนดนี้

### Account scope amendment — 2026-11-13 — บัญชี ECM เฉพาะ Folio

ผู้ใช้เปลี่ยนข้อกำหนดเป็นบัญชี ECM แยกสำหรับ Folio ให้ Folio จัดการ login/token เองโดยไม่พึ่งหรือแก้ Ongoing และจะมี username/password ใหม่ภายหลัง ข้อนี้แทนข้อจำกัดว่าต้องใช้บัญชีร่วมในบันทึกเก่า ไม่ใช่การเปลี่ยนข้อเท็จจริงของ endpoint อัปโหลด/ลบหรือการยืนยันผล runtime

ให้ยึด [ECM login และ token ของ Folio ด้วยบัญชีแยก](13-folio-ecm-auth.md) เป็นเจ้าของแผน auth ปัจจุบัน หัวข้อใช้บัญชีร่วมปิดเป็น out of scope แล้ว ยังไม่ยืนยันสิทธิ์หรือผล login ของบัญชีใหม่ และห้ามใช้บัญชี/token ของ Ongoing เป็น fallback
