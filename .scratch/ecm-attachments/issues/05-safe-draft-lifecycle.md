## Question

เมื่อ User กด Save Draft หรือ Submit ต้องทำอะไรกับไฟล์ใหม่ ไฟล์เดิม เอกสาร และข้อมูลคำตอบ และเมื่อใดจึงนับว่าการบันทึกสำเร็จ โดยไม่ทำไฟล์เดิมหายและไม่เหลือไฟล์ร่างเก่าหลังการแทนที่เสร็จ?

ตัดสินการแทนที่/ลบในร่าง, ไม่เปลี่ยนไฟล์, เลือกแล้วออกจากหน้า, เปิดร่างต่อ, ลบแถว, หลายช่องที่สำเร็จไม่พร้อมกัน, ECM รับไฟล์แต่ตอบกลับไม่ถึง, บันทึก Folio ไม่สำเร็จ และลบเก่าไม่สำเร็จ รวมพฤติกรรมเมื่อกดซ้ำหรือเปิดหลายแท็บเท่าที่ต้องรักษาความถูกต้อง ระบุสิ่งที่ผู้ใช้ต้องทำต่อ ไม่เพิ่มกลไก retry หรือระบบงานใหม่โดยไม่มีเหตุจากข้อจำกัดจริง

ข้อกำหนดที่ยืนยันคือไม่ค้างและไม่สูญหาย ไม่ใช่บังคับลบเก่าก่อนอัปโหลดใหม่ ต้องใช้ความสามารถ API ที่วิจัยแล้วและรักษา invariant ของ Draft/Submission เดิม

ใช้ representation และ mapping ที่ยืนยันใน [สัญญา JSON ของไฟล์แนบและ URL ใน Excel](11-attachment-json-contract.md) แล้วกำหนดลำดับบันทึกให้ข้อมูลและเอกสารเป็น revision เดียวกัน ไม่เขียนผลสำเร็จลงเพียงด้านเดียวหรือทำ metadata ที่ใช้ลบ/รักษาประวัติหาย

## Comments

### Discussion — ลำดับบันทึกและกรณีที่ยังต้องตัดสิน

#### Current behavior — ตรวจจาก source

- [completeDraftOperation และ completeSubmitOperation](../../../apps/server/src/operations/response-completion.ts) บันทึกตัวอ้างอิงเอกสารกับ JSON ใน transaction เดียวกัน และตรวจสถานะ/ฉบับก่อน commit; การสร้าง Correction ตรวจ base revision และ workspace เพิ่มด้วย ไม่พบการจัดการไฟล์ ECM ใน flow ที่ตรวจนี้
- [createOperation](../../../apps/server/src/operations/create.ts) ตรวจสิทธิ์ editor/lease และไม่รับ operation ซ้อนของ target เดียวกัน; [lifecycle](../../../apps/server/src/operations/lifecycle.ts) ทำให้ operation ที่เกินเวลาล้มเหลวได้ การหมดเวลาใน Folio จึงใช้เป็นหลักฐานว่า ECM ไม่ได้สร้างไฟล์ไม่ได้
- [object-cleanup](../../../apps/server/src/operations/object-cleanup.ts) มีการตรวจ canonical references ก่อนลบ object ของ Folio และมี cleanup intents ส่วน [การลบ Response](../../../apps/server/src/responses/deletion.ts) ใช้ tombstone/cleanup metadata เพื่อให้ตามลบต่อได้หลังลบข้อมูลหลัก กลไกนี้ยังไม่ใช่ receipt หรือ cleanup ของ ECM และไม่ควรคัดลอกโดยถือว่าป้องกัน race ข้ามระบบได้แล้ว
- [หลักฐานสัญญา ECM](09-provider-contract-evidence.md) ยังไม่มีหลักฐานยืนยันผลคำขอที่ไม่แน่ชัดหรือ idempotency; การตรวจผ่านหน้า DCM ไม่ทำให้การค้นไม่พบครั้งเดียวเป็นหลักฐานว่าคำขอจบโดยไม่สร้างไฟล์
- ใช้ auth ตาม [ECM login และ token ของ Folio ด้วยบัญชีแยก](13-folio-ecm-auth.md): ไม่ใช้บัญชี Ongoing และไม่ขยาย retry ของ login ไปเป็นการส่ง upload/delete ซ้ำ

#### Intended behavior — ฐานที่ยืนยันแล้วและข้อเสนอที่ยังไม่ใช่ resolution

- คง snapshot เดิมเมื่อการบันทึกล้มเหลวตาม [สัญญา JSON](11-attachment-json-contract.md) ไม่บันทึกบางช่องโดยรายงานว่าทั้งรอบสำเร็จ
- เสนอลำดับอัปโหลดฉบับใหม่ให้ได้ผลที่ตรวจแล้วครบก่อน จากนั้นบันทึกเอกสารกับ JSON ของฉบับเดียวกัน แล้วจึงลบไฟล์เก่าของ Folio ที่ไม่มี references เหลือ การบันทึกใหม่กับการลบเก่าเป็นคนละผลลัพธ์ ห้าม rollback กลับไปอ้างไฟล์ที่อาจถูกลบไปแล้ว
- ต้องมีข้อมูลคำขอ/ชื่อฉบับที่วางแผนไว้ก่อนเริ่ม external write และเก็บ receipt/งานลบที่ตรวจสอบได้อย่างคงทน ไม่อาศัย browser หรือ operation ที่หมดเวลาเพียงอย่างเดียว ไม่ใช้ URL/token จาก client เป็นสิทธิ์ลบ

#### รอผู้ใช้ตัดสิน

1. เมื่อบางไฟล์อัปโหลดสำเร็จแต่ทั้งรอบบันทึกไม่สำเร็จ ให้ยกเลิกรอบและตามลบเฉพาะไฟล์ใหม่ที่ไม่มี references แล้วกดบันทึกใหม่ หรือเก็บ receipt ที่สำเร็จไว้ใช้ต่อเฉพาะเมื่อพิสูจน์ได้ว่าเป็นไฟล์/metadata/ช่อง/ขอบเขตเดิม?
2. เมื่อไม่ทราบว่า ECM รับคำขอแล้วหรือไม่ ยอมให้ PM/ผู้ดูแล ECM ตรวจและยืนยันว่าคำขอจบพร้อมจัดการไฟล์ค้างก่อนปลดการบันทึกของคำตอบนี้ หรือกำหนดว่าต้องยืนยันผลผ่าน API ได้ก่อนเปิดใช้ฟีเจอร์? ไม่ถือว่าการค้นไม่พบหรือ timeout เป็นการยืนยันว่าไม่เกิดไฟล์
3. เมื่อเอกสารกับ JSON ใหม่บันทึกแล้วแต่ลบไฟล์เก่าไม่สำเร็จ ให้ทำงานต่อได้พร้อมสถานะลบค้างที่ติดตามได้ หรือหยุดการแก้/ส่ง/ลบคำตอบนี้จนยืนยัน cleanup? ทั้งสองทางต้องแสดงว่าข้อมูลใหม่บันทึกแล้ว และ URL เก่าอาจยังเปิดได้จนลบสำเร็จ

ยังต้องสรุปผลต่อการเลือกแล้วออกจากหน้า การเปิดร่างต่อ การลบแถว การกดซ้ำ/หลายแท็บ การบันทึก workspace ของ Correction และการกู้คืนหลัง process หยุด โดยไม่ขยายสิทธิ์หรือสร้าง retry อัตโนมัติจากข้อเสนอข้างต้น

หลักฐานรอบนี้เป็นการอ่าน source และสัญญาที่บันทึกไว้ ไม่ได้แก้ application, เรียก ECM, ใช้ credentials หรือทดสอบกับ DB/ONLYOFFICE จริง

### Resolution — ยืนยันร่วมกับผู้ใช้

ผู้ใช้เลือก **ยกเลิกรอบและลบไฟล์ใหม่**, **ให้ผู้ดูแลยืนยันผลอัปโหลดที่ไม่แน่ชัด** และ **ทำงานต่อได้หลังบันทึกพร้อมแจ้งลบค้าง** ข้อสรุปนี้แทนคำถามที่รอคำตอบใน Discussion ด้านบน เป็นแผน ไม่ใช่การอนุญาตให้เรียก ECM หรือพัฒนาแอปจริง

#### ลำดับบันทึกและขอบเขต

1. เริ่มจากการกด Save Draft/Submit ของ User หรือบันทึก Correction ของ Admin ที่มีสิทธิ์เท่านั้น ตรวจสิทธิ์/lease, Published Template, base document/revision, binding/แถว, metadata, ไฟล์ และกติกา required ที่ตรวจได้ก่อน external write ตามตั๋วเจ้าของข้อกำหนด ไม่เริ่มอัปโหลดจากการเลือกไฟล์ การเผยแพร่ Template หรือการบันทึกภายในเพื่อเลือกโครงการ
2. จับ snapshot ของเอกสาร ข้อมูล คำสั่งแถว และไฟล์ที่จะใช้ในรอบเดียวกัน บันทึก operation และ intent ของแต่ละฉบับอย่างคงทนก่อนส่งออก รวมชื่อฉบับเฉพาะและขอบเขตที่ตรวจแล้ว ใช้ transaction สั้น ไม่ถือ DB lock ระหว่างเรียก ECM
3. ส่งไฟล์ทีละไฟล์ต่อ operation และหยุดเริ่มไฟล์ถัดไปเมื่อมีปัญหา เก็บผล upload ที่ตรวจแล้วกับ intent เดิมทันที ไม่สร้าง receipt จากชื่อไฟล์หรือข้อความใน cell การรับผลล่าช้าต้องยังตามกลับไปยัง intent เดิมได้ แม้ operation หมดเวลาหรือถูกยกเลิก
4. เมื่อได้ผลครบ ให้ประกอบ URL ใน workbook และ file objects ใน JSON จาก snapshot เดียวกัน ตรวจ schema, required, mapping และขอบเขต JSON รวม metadata อีกครั้งก่อน commit ตรวจสิทธิ์/ฉบับ/operation ที่ยังใช้ได้ใน transaction แล้วบันทึกคู่เอกสารกับ JSON และผล operation พร้อมกันตาม invariant เดิม ไม่สร้าง Submission/Correction หรือเปลี่ยนเฉพาะ JSON เมื่อยังได้ไฟล์ไม่ครบ
5. หลัง commit จึงเริ่มลบไฟล์เก่าของ Folio ที่ไม่มีฉบับหรือ operation ที่ยังใช้ได้อ้างถึง การเปลี่ยนไฟล์จึงไม่เขียนทับหรือลบไฟล์เดิมก่อนมีฉบับใหม่ที่บันทึกแล้ว ไฟล์ที่ประวัติยังใช้อยู่เป็นการเก็บตามนโยบาย ไม่ใช่ไฟล์ลบค้าง

ไฟล์และ metadata ที่ไม่เปลี่ยนใช้ references เดิม ไม่เรียก upload/login เพียงเพราะกดบันทึก การเปลี่ยนเลขหรือปีใช้ไฟล์ที่เลือกใหม่ หรืออ่าน bytes ของไฟล์ที่บันทึกแล้วมาอัปโหลดฉบับใหม่ตาม [กติกาชื่อไฟล์](04-confirmation-filename.md) ต้องตรวจ URL/ปลายทางการอ่านฝั่ง server ไม่เปิดให้ client ระบุ URL อิสระเพื่อให้ server ไปอ่าน หากอ่านไม่ได้ให้หยุดโดยรักษาฉบับปัจจุบัน ไม่บังคับเลือกไฟล์เดิมใหม่เป็นวิธีหลบข้อกำหนด

#### ผลล้มเหลวและสิ่งที่ผู้ใช้ทำต่อ

| เหตุการณ์ | ผลที่ต้องรักษาและการทำต่อ |
| --- | --- |
| ตรวจข้อมูล/ไฟล์/แถวไม่ผ่านก่อนส่ง | ไม่เริ่ม external write แจ้ง Field/ช่อง/แถวที่ต้องแก้ คงฉบับที่บันทึกแล้วและไฟล์ที่เลือกในหน้าปัจจุบัน |
| บางไฟล์สำเร็จ แต่ทั้งรอบยัง commit ไม่ได้ | ยกเลิกทั้งรอบ ไม่บันทึกบางส่วน ไม่ใช้ receipt รอบที่ยกเลิกซ้ำในรอบใหม่ ตามลบเฉพาะไฟล์ใหม่ที่ยืนยันได้และไม่มี references ก่อนให้กดบันทึกใหม่ หากลบไม่ได้หรือยังไม่ทราบผล ให้คงงานติดตามและหยุดการเปลี่ยนแปลงคำตอบนี้จนเคลียร์ครบ |
| Folio ยืนยันว่า transaction ไม่ commit | คง canonical ฉบับปัจจุบันและไฟล์เดิม ยกเลิก/ตามลบไฟล์ใหม่เช่นเดียวกับกรณีสำเร็จบางส่วน การส่งใหม่เกิดจากการกดของ User และใช้ identity ฉบับใหม่ ไม่ใช้ไฟล์รอบที่ยกเลิกเป็น cache |
| ไม่ทราบผล commit หรือ response ของ Folio หาย | ตรวจ operation/checkpoint และฉบับที่บันทึกจริงใน Folio ก่อน ห้ามเดาว่าล้มเหลวแล้วลบไฟล์ใหม่ซึ่งอาจถูกบันทึกอ้างถึงแล้ว หาก commit แล้วให้คืนผลเดิม ไม่สร้าง upload/Submission/Correction ซ้ำ หาก DB ยังตรวจไม่ได้ให้แสดงว่ากำลังยืนยันผล ไม่รายงานสำเร็จหรือ rollback |
| Upload timeout, process หยุดหลังเริ่มส่ง หรือผลตอบกลับไม่มีหลักฐาน URL/token ที่ใช้ได้ | ถือว่าไม่ทราบผล ไม่ใช่ไม่มีไฟล์ ร่างเดิมยังอ่านได้ แต่หยุดการบันทึก ส่ง และลบคำตอบนี้จนผู้ดูแลยืนยันผลและจัดการไฟล์ค้างครบ ห้ามส่ง upload เดิมซ้ำหรือเลือกไฟล์ล่าสุดจากการค้นมาใช้แทน |
| เอกสารกับ JSON ใหม่ commit แล้ว แต่ลบไฟล์เก่าไม่สำเร็จ/ยังไม่ทราบผลลบ | ข้อมูลใหม่บันทึกแล้ว ใช้และ export URL ใหม่ต่อได้ พร้อมสถานะลบค้างที่ติดตามได้ ทำงานต่อได้ตามที่ผู้ใช้เลือก ไม่ rollback หรือรายงานว่าข้อมูลใหม่หาย URL เก่าอาจยังเปิดได้จนยืนยันว่าลบแล้ว |
| พบคำตอบ/เอกสาร/workspace เปลี่ยนระหว่างทำงาน | ไม่เขียนทับฉบับที่ชนะด้วย snapshot เก่า ไม่ย้าย receipt ไปใส่ฉบับใหม่โดยคาดเดา ยกเลิกรอบเดิมและติดตามไฟล์ใหม่ตามสถานะจริง ให้เปิดฉบับปัจจุบันก่อนเริ่มรอบใหม่ |

ผลอัปโหลดที่ยังไม่แน่ชัดต้องไม่กลายเป็น file object ที่นับว่าแนบสำเร็จ ข้อจำกัด login/retry ให้ยึด [แผน auth ของ Folio](13-folio-ecm-auth.md) ไม่ขยายไปเป็นการส่ง upload/delete ซ้ำเอง การตามลบครั้งแรกเป็นส่วนหนึ่งของรอบที่ User เริ่ม ส่วนผลลบที่ค้างต้องมีการติดตาม/การกระทำของผู้ดูแลที่ตรวจสิทธิ์และสถานะอีกครั้ง ไม่เพิ่ม retry daemon หรือ queue ใหม่จาก resolution นี้

#### ไฟล์ที่เลือก การเปิดร่าง และคำสั่งแถว

- การเลือก/เปลี่ยนไฟล์ก่อนกดบันทึกเปลี่ยนเฉพาะ pending selection ไฟล์เดิมที่บันทึกแล้วยังอยู่ การยกเลิก selection กลับมาใช้ข้อมูลที่บันทึกแล้วได้ก่อนเริ่มรอบบันทึก ไม่มีคำสั่งลบ ECM ทันทีจากปุ่มนำออก
- แจ้งก่อนออกจากหน้า เปลี่ยนบัญชี/คำตอบ หรือทำให้ pending selections หาย การคง File ในหน้าปัจจุบันไม่ใช่ persistence และไม่รับรองว่าจะอยู่หลัง reload/ปิดหน้า กลับมาเปิดร่างต้องใช้ canonical เอกสารกับ JSON ที่บันทึกแล้ว หากไฟล์ใหม่ยังไม่เคยบันทึกสำเร็จต้องเลือกใหม่
- การนำไฟล์ออกหรือลบแถวที่ระบบอนุญาตเป็นคำสั่งรอบถัดไป ก่อนบันทึกยังไม่ลบต้นทาง หลัง commit จึงตรวจ references และตามลบเฉพาะไฟล์ที่ไม่ถูกใช้แล้ว หากการลบแถวไม่รองรับตามสัญญาเดิม ให้ปฏิเสธ ไม่เพิ่มสิทธิ์หรือความสามารถลบแถวเพียงเพื่อให้ไฟล์แนบผ่าน
- คำสั่งแถวที่รองรับต้องปรับ mapping ของ pending files และ canonical metadata จาก workbook/คำสั่งที่ตรวจแล้วในรอบเดียวกัน ไม่ผูกไฟล์กับ index ของ JSON array ที่ถูก compact ไม่อัปโหลดใหม่เพียงเพราะแถวเลื่อน และไม่ย้ายไฟล์เมื่อพิสูจน์ mapping ไม่ได้
- ใช้ [กติกาไฟล์และแถว required](07-pdf-acceptance.md) รวมไฟล์ 0 bytes และแถวที่มีแต่ไฟล์ ไม่ใช้ความจริงเท็จของขนาดไฟล์หรือชื่อไฟล์เป็นหลักฐานว่าแนบสำเร็จ ไฟล์ที่เลือกไม่ถูกต้องยังทำให้ Save Draft ไม่ผ่าน
- การบันทึก workspace/การเลือกโครงการภายใน Correction ไม่ใช่การบันทึก Correction สำเร็จและไม่เริ่ม upload ต้องรักษา pending selections ระหว่างการเปลี่ยน document key ภายใน workspace เดิมได้เฉพาะเมื่อมี transition/mapping ที่ตรวจแล้ว หากรักษาไม่ได้ให้หยุดก่อน reload/ทิ้งไฟล์และแจ้งผู้ใช้ ไม่ถือว่าต่างบัญชี/ต่างคำตอบเป็น workspace เดียวกัน ไฟล์เริ่มส่งเมื่อ Admin กดบันทึก Correction พร้อมเหตุผลและสิทธิ์ที่ถูกต้อง

#### การกดซ้ำ หลายแท็บ และการกู้คืน

- ใช้ operation/checkpoint, actor/target และ base revision ที่ตรวจแล้วเพื่อรู้ว่ารอบใดกำลังทำหรือเสร็จแล้ว ป้องกันกดซ้ำทั้ง UI และ server ไม่อาศัยปุ่ม disabled เป็นหลักฐานสิทธิ์ ไม่เริ่ม external writes อีกชุดจากการ poll/reload/ผลตอบกลับซ้ำ
- คงกติกา editor lease และการตรวจ stale ของระบบเดิม ไม่ยอมให้หลายแท็บหรือ callback เก่าเขียนทับฉบับปัจจุบัน การล้าง pending selection เมื่อสำเร็จต้องตรงกับ selection/snapshot ที่รอบนั้นรับไป ไม่ล้างการแก้ใหม่ที่ไม่ได้อยู่ใน snapshot
- ผลที่บันทึกอย่างคงทนต้องแยกให้ได้ว่า ยังไม่ได้เริ่มส่ง, เริ่มส่งแต่ไม่ทราบผล, ได้ receipt แต่ยังไม่ commit, commit แล้ว, หรือมีงานลบค้าง การหมดเวลา/เริ่ม process ใหม่ไม่ทำให้ intent ที่เริ่มส่งกลับเป็นงานที่ปลอดภัยให้ส่งซ้ำ
- เมื่อกู้คืน พบ receipt ที่ยังไม่ commit ให้ยกเลิกและตามลบตามนโยบาย ไม่ adopt ไปยังรอบใหม่ พบ commit แล้วให้คืนผลเดิมและรักษางานลบค้าง ส่วนผลล่าช้าของรอบที่ยกเลิกต้องเก็บเพื่อ cleanup ไม่ใช้ทำให้รอบนั้นกลับมา commit
- ไม่ใช้ staged/failed workbook ที่อาจมี URL ของไฟล์ที่ยกเลิกแล้วเป็น canonical หรือร่างที่เปิดต่อโดยอัตโนมัติ การกู้ข้อมูลต้องรักษา mapping และขอบเขตเดียวกัน ห้ามฟื้น references ของไฟล์ที่ถูกลบหรือกำลังลบ

#### สิทธิ์ลบและการยืนยันผลโดยผู้ดูแล

- ลบได้เฉพาะไฟล์ที่มีหลักฐานว่า Folio อัปโหลดและไม่มี references ที่ยังใช้ได้ รวม Draft, Submission, Correction, workspace และ operation ที่ยอมให้ใช้ไฟล์นั้น ไม่ใช้ token/URL ที่ client ส่งมาเป็นอำนาจลบหรือแค่สแกนข้อความที่ดูเหมือน URL
- การตรวจไม่มี references และการ claim ลบต้องกัน race กับ transaction ที่กำลังเพิ่ม references ด้วย เมื่อไฟล์ถูก claim ลบหรือผลลบยังไม่แน่ชัด ห้ามสร้าง references ใหม่มาชี้ไฟล์นั้น ไม่คัดลอกวิธี query-then-delete ของ object storage โดยถือว่าปลอดภัยข้ามระบบเอง
- ข้อมูล intent/receipt/cleanup เป็น operational records ที่ต้องอยู่รอดหลัง process หยุดหรือข้อมูลหลักถูกลบ ไม่ใช่การย้าย metadata ออกจาก JSON เพื่อหลบขอบเขตขนาด [สัญญา JSON](11-attachment-json-contract.md) และสิทธิ์ [ประวัติ/การลบทั้งคำตอบ](06-history-access.md) ยังคงเดิม
- เมื่อไม่ทราบผล upload ให้ Folio Admin ประสาน PM/ผู้ดูแล ECM ด้วย operation, ชื่อฉบับเฉพาะ, ปี, category และช่วงเวลาส่งที่บันทึกไว้ ต้องยืนยันว่า worker/คำขอเดิมจะไม่ส่งหรือเขียนต่อได้อีก และคำขอที่ถึง ECM จบแล้ว การค้นไม่พบเพียงครั้งเดียวหรือรอจนหมดเวลาไม่พอ
- หากพบไฟล์ของรอบที่ยกเลิก ผู้ดูแลที่มีสิทธิ์ต้องจัดการลบให้ครบ ไม่ adopt มาเป็นคำตอบที่สำเร็จ หากยืนยันว่าไม่เกิดไฟล์ต้องมีหลักฐานว่าคำขอจบจริง Folio Admin จึงบันทึกผู้ยืนยัน ผล และหลักฐานเพื่อปลดการติดตาม หากยังยืนยันไม่ได้ให้คงสถานะค้าง ไม่ใช้ checkbox/URL/token ที่กรอกเองเป็นข้อพิสูจน์หรือสิทธิ์ลบอัตโนมัติ
- การตรวจของผู้ดูแลต้องไม่ login ทับบัญชีบริการ Folio นอกระบบประสาน token ที่ตกลงไว้ การลบที่ค้างหลัง commit ไม่ทำให้ข้อมูลใหม่ใช้ไม่ได้ และไม่ปลดเงื่อนไข references/สิทธิ์เพียงเพราะ User ทำงานต่อได้
- เมื่อลบทั้ง Response ต้องคงข้อมูลสำหรับตามลบไฟล์ทุกฉบับและ intent ที่เกี่ยวข้องก่อนลบ rows หากข้อมูล Folio ถูกลบแล้วแต่ไฟล์ยังค้างให้แสดงผลสองส่วนนี้ตรงจริง ไม่รายงานว่าลบทุกไฟล์ครบหรือทำ tombstone/cleanup metadata หาย การ archive ไม่ใช่การลบ

#### ขอบเขตส่งต่อและหลักฐาน

- ขั้นพัฒนาต้องครอบคลุมการรับ operation/callback/timeout, การบันทึก Draft/Submit/Correction/workspace, validation/extraction/projection ของเอกสารและ JSON, pending selections/คำสั่งแถวใน editor และการลบ Response พร้อม recovery/cleanup ไม่เพียงถอด guard ของ PoC หรือเพิ่ม POST ไป ECM จุดเดียว
- [หน้าตั้งค่าปลายทางและสถานะไฟล์ที่ผู้ใช้เข้าใจ](08-admin-user-prototype.md) เป็นเจ้าของหน้าจอ/ข้อความ/การโต้ตอบ รวมสถานะต้องตรวจผลโดยผู้ดูแลและบันทึกแล้วแต่ลบค้าง ไม่มีการเลือก UI แทนผู้ใช้จาก resolution นี้
- ก่อนเปิดใช้งานจริงต้องมีบัญชี Folio/สิทธิ์ที่เหมาะสมตามแผน auth และผู้ดูแลที่ยืนยันผล/จัดการไฟล์ค้างได้จริง ต้องตรวจ response/error semantics, การอ่าน bytes เดิมอย่างปลอดภัย, ไฟล์ตามขอบเขตที่รับ, deadline ของ operation และ race/crash windows กับระบบจริง ไม่ถือว่าค่าหมดเวลาของ login เป็นค่าหมดเวลาของการส่งไฟล์โดยอัตโนมัติ
- รอบนี้ตรวจ source ผ่าน CodeGraph และส่วนที่ขาด ตรวจสถานะตั๋ว prerequisites และลิงก์ใน tracker ไม่มี application/schema/config/export/fixture หรือ permanent test เปลี่ยน ไม่ได้ทดสอบ ECM, DB, ONLYOFFICE, XLSX/PDF หรือการกู้คืนจริง จึงไม่อ้างว่ารับประกัน runtime แล้ว
