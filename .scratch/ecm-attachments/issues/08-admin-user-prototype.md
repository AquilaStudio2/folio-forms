## Question

จะเสริม category/tag/required ในการตั้งค่า Field เดิม และแสดงไฟล์ที่เลือก URL ที่บันทึกแล้ว กับสถานะผิดพลาดบนปุ่ม upload PoC เดิมของ Excel อย่างไร ทั้งช่องเดี่ยวและตาราง โดยคงตำแหน่ง/binding และ flow เดิมเป็นฐาน ไม่สร้างหน้า upload หรือ editor ใหม่มาแทน และใช้ URL ของฉบับที่กำลังดูในหน้าดู/ส่งออก?

หารือด้วยโครงร่างข้อความหรือภาพในแผนที่อ้างตำแหน่ง UI เดิม ครอบคลุมการแทนที่/นำออก การบันทึก/ส่งที่ล้มเหลว การเปิดร่างต่อ และ keyboard access/labelled controls ตามข้อสรุปตั๋วเจ้าของนโยบาย ไม่สร้าง prototype code เพิ่ม ไม่ใช้เดโมแยกเป็นฐานพัฒนา และไม่พัฒนาหรือเรียก ECM จริงจนผู้ใช้สั่งเริ่มขั้นพัฒนา

### กรณีวงจรไฟล์ที่ตกลงแล้ว

ใช้ [วงจรไฟล์ร่างและการบันทึกโดยไม่สูญหาย](05-safe-draft-lifecycle.md) เป็นเจ้าของผลการบันทึกและการกู้คืน ออกแบบหน้าจอให้ผู้ใช้ตอบรับจริง ไม่เปลี่ยนนโยบายหรือทำระบบ ECM ใน prototype นี้

- แยกไฟล์ที่เพิ่งเลือกกับ URL ของไฟล์ที่บันทึกแล้วให้เห็นชัด รวมการยกเลิก selection นำไฟล์ออก แถวเปลี่ยนตำแหน่ง และคำเตือนก่อนออกจากหน้า/เปลี่ยนขอบเขตจน File หาย ไม่แสดงว่าไฟล์ถูกเก็บถาวรเพียงเพราะเลือกแล้ว
- เมื่อบางไฟล์อัปโหลดสำเร็จแต่ทั้งรอบล้มเหลว ให้เห็นว่าฉบับเดิมไม่เปลี่ยน รอบใหม่ต้องเริ่มหลังจัดการไฟล์ของรอบที่ยกเลิกครบ ไม่เสนอใช้ receipt รอบเดิมหรือ retry upload/delete อัตโนมัติ
- เมื่อไม่ทราบผล upload ให้เห็นว่าร่างเดิมยังอ่านได้ แต่บันทึก ส่ง และลบคำตอบนี้ไม่ได้จนผู้ดูแลยืนยันผล แยกจากการรอ operation ปกติ ไม่ทำ spinner ค้างโดยไม่มีคำอธิบายหรือสิ่งที่ผู้ใช้ทำต่อ
- ออกแบบส่วนติดตามของ Folio Admin สำหรับประสาน PM/ผู้ดูแล ECM ด้วยข้อมูล intent ที่ตรวจแล้วและบันทึกหลักฐานยืนยัน ไม่เปิดให้กรอก URL/token ใดก็ได้แล้วลบหรือ adopt เป็นคำตอบที่สำเร็จ การค้นไม่พบครั้งเดียวไม่ใช่ปุ่มลัดปลดค้าง
- เมื่อเอกสารกับ JSON ใหม่บันทึกแล้วแต่ลบเก่าค้าง ให้เห็นทั้งผลบันทึกและคำเตือน ใช้งาน/ส่งออก URL ใหม่ต่อได้ และไม่สื่อว่า URL เก่าถูกลบแล้ว อย่าย้อนกลับไปแสดงข้อมูลเก่าเป็น canonical
- ครอบคลุม response ของ Folio หาย กดซ้ำ หลายแท็บ และกลับมาเปิดใหม่ โดยตรวจผล operation เดิมก่อนเสนอเริ่มรอบใหม่ แยกสถานะผู้ใช้ Folio ออกจากข้อผิดพลาด ECM login ตาม [แผน auth](13-folio-ecm-auth.md)
- การเลือกโครงการ/บันทึก workspace ภายใน Correction ต้องไม่เริ่ม upload หรือทิ้ง pending selections โดยเงียบ แสดงผลสำเร็จของไฟล์เมื่อบันทึก Correction จริงเท่านั้น ยังคงเหตุผล สิทธิ์ และกติกา revision เดิม
- ไฟล์ที่ประวัติยังใช้อยู่ไม่ใช่ลบค้าง ส่วนการลบทั้ง Response ที่ลบข้อมูลแล้วแต่ยังตามลบไฟล์ไม่ครบต้องสื่อผลสองส่วนตามจริง ไม่เปลี่ยนขอบเขตการลบที่ตกลงแล้ว

### Scope clarification — คุยแผนอย่างเดียวก่อน

ผู้ใช้เลือกให้พักการเขียนโค้ดทดลองและคุยเฉพาะแผนก่อน ไม่ถือว่าได้อนุมัติหน้าจอหรืออนุญาตให้พัฒนาฟีเจอร์จริง ตั๋วนี้ยังไม่ resolved และยังไม่มี resolution ของ UI

- พัก prototype สามรูปแบบที่เขียนไว้ใน worktree `/tmp/folio-ecm-attachment-ui-20261113` บน branch `prototype/folio-ecm-attachment-ui-20261113` โดยไม่ลบและไม่เขียนเพิ่ม ไฟล์ทดลองยังไม่ได้ commit/push/merge เข้า main
- ปิด browser tab และหยุด preview server แล้ว ไม่ได้เชื่อม ECM ใช้ credentials หรือแก้ DB งานทดลองไม่ใช่ผลพิสูจน์ integration/runtime จริง
- ประเด็นที่ยังรอคุยคือการวางการตั้งค่า category/tag รายช่อง/คอลัมน์ และการแสดงไฟล์ที่เลือก URL ที่บันทึกแล้ว ข้อผิดพลาด ผลไม่แน่ชัด และลบค้าง ตามนโยบายที่ตั๋วอื่นตัดสินแล้ว
- สนทนาต่อด้วยข้อเสนอในแผน ไม่เริ่มเขียน prototype หรือ application เพิ่มเอง และไม่ปิด map จนผู้ใช้ยืนยันหัวข้อนี้จริง

### Scope correction — ต่อจากปุ่ม PoC เดิม ไม่ใช่สร้าง UI ใหม่แทน

ผู้ใช้ย้ำว่าต้องการทำงานต่อจากปุ่ม PoC ที่มีอยู่แล้ว นี่คือการยืนยันเจตนาเดิม ไม่ใช่คำขอให้สร้างระบบอัปโหลดหรือหน้า editor อีกชุด ผู้ช่วยขยายการทดลองหน้าจอแยกเกินความจำเป็น จึงแก้ขอบเขตหัวข้อนี้กลับมาเป็นการหารือส่วนที่ต้องเสริมใน UI เดิม และเปลี่ยนประเภทเป็น `wayfinder:grilling`

- ยึดปุ่มในชีต ตำแหน่ง tag/binding และการตั้งค่า Field เดิมเป็นฐาน ตาม [นโยบายต่อยอด PoC](12-poc-form-cutover.md) ไม่สร้างปุ่มหรือหน้ากรอกอีกชุดมาแทน การตั้ง category เป็นการเสริมการตั้งค่าเดิมรายช่อง/คอลัมน์
- ส่วนพัฒนาภายหลังคือทำให้ปุ่มเดิมทำงานครบตามสัญญาที่ตัดสินแล้ว รวม server-side auth, upload เมื่อบันทึก/ส่ง, JSON/URL, การรักษาประวัติ และ cleanup ไม่ใช่การนำโค้ดเดโมแยกไปใช้แทนการเชื่อม PoC จริง
- ไม่เปิดการเปลี่ยน Published Template ย้อนหลังจากคำย้ำนี้: Template Draft ใช้ช่องเดิมที่ตรวจ binding ได้ ส่วนฟอร์มที่เผยแพร่แล้วทำสำเนา/คงสัญญาเก่าตามตั๋วเจ้าของนโยบาย
- prototype แยกยังพักไว้ ไม่ merge ไม่ใช้เป็นฐานพัฒนา ไม่ต้องเลือกหนึ่งในสาม layout เป็นเงื่อนไขเริ่มพัฒนา และไม่เปลี่ยน flow เดิมโดยไม่มีเหตุจากข้อกำหนดจริง
- ผู้ใช้ยังเลือกให้คุยแผนก่อน จึงไม่เริ่มเขียนฟีเจอร์จริงหรือปิดหัวข้อนี้จากคำชี้แจงเพียงอย่างเดียว

### Discussion — ส่วนที่ต้องเสริมบน UI เดิม

#### Current behavior — ตรวจจาก source

- [แผงตั้งค่า Excel เดิม](../../../apps/onlyoffice-plugin/src/spreadsheet.js) มีการเลือกช่องที่บันทึกแล้ว Title, Tag, ชนิดข้อมูล และบังคับกรอกอยู่ใน Template Edit จึงมีจุดสำหรับเสริม category ของช่อง/คอลัมน์ ไม่ต้องสร้างหน้าสร้างฟอร์มอีกชุด
- [กล่องปุ่ม PoC เดิม](../../../apps/onlyoffice-plugin/src/upload-poc-picker.js) มี input เลือกไฟล์ ชื่อ ขนาด และ status อยู่แล้ว ส่ง File ให้ host เก็บในหน่วยความจำ ไม่ upload หรือเขียน workbook; [host](../../../apps/web/src/features/onlyoffice/upload-poc-pending.ts) ยังกัน Save/Submit ที่มีไฟล์ค้าง จึงยังไม่ใช่ flow บันทึกไฟล์จริง

#### ฐานที่คงตามข้อสรุปเดิม

- Admin ตั้ง category จากรายการ API เพิ่มในแผง Field เดิม ใช้ Tag/required และ binding เดิม คอลัมน์ใช้ category ร่วมทุกแถว ไม่เพิ่มหน้าหรือค่าปีจัดเก็บแยก และไม่เปิดแก้หลังเผยแพร่
- หน้าอ่านและ export ใช้ URL ของฉบับที่เลือกแทนปุ่ม ไม่เปิด picker ส่วน Draft/Correction ที่มีสิทธิ์ต้องเปลี่ยน/นำไฟล์ออกได้ การเปิด URL ไม่ใช่การเลือกไฟล์ใหม่
- เลือกไฟล์ยังไม่บันทึก ต้องแยกไฟล์ที่เลือกกับไฟล์ที่บันทึกแล้ว การนำออกเป็นรายการเปลี่ยนแปลงรอบถัดไปพร้อมยกเลิกได้ก่อนบันทึก ไม่ลบ ECM ทันที และไม่ใช้คำสั่งลบปุ่มต้นแบบเป็นคำสั่งลบไฟล์
- สถานะไม่ทราบผล upload ต้องหยุดการเปลี่ยนแปลงคำตอบพร้อมบอกให้ติดต่อผู้ดูแล ส่วนบันทึกแล้วแต่ลบค้างให้ใช้ข้อมูลใหม่ต่อได้ตาม [วงจรไฟล์](05-safe-draft-lifecycle.md) ไม่สร้างปุ่ม retry ที่ส่ง write ซ้ำหรือปลดค้างจาก token/ข้อความที่กรอกเอง

#### Frontier ที่รอคำตอบในรอบนี้

1. หน้าแก้ Draft/Correction จะใช้กล่องเดิมของปุ่ม PoC แสดง URL ปัจจุบัน ไฟล์ที่เลือก และคำสั่งเปลี่ยน/นำออก หรือแสดงคำสั่งข้าง URL ในชีต? แนะนำกล่องเดิมเพื่อไม่เพิ่ม drawing/พื้นที่ controls ในชีต
2. สถานะผิดพลาด/ไม่ทราบผล/ลบค้างจะแสดงเป็นข้อความค้างในหน้ากรอกเดิม หรือ badge ค้างพร้อมเปิดรายละเอียด? ทั้งสองแบบต้องบอกช่อง/แถวและสิ่งที่ทำต่อ ไม่หายไปเพียงเพราะ toast หมดเวลา แนะนำข้อความค้างที่อ่านได้ทันที
3. Admin จะดูรายละเอียดติดตามโดยขยายส่วนในหน้าผลลัพธ์เดิม หรือเปิดกล่องรายละเอียดจากหน้าเดิม? ใช้ข้อมูล intent/ผลตรวจที่ server อนุญาตเท่านั้น ไม่สร้างหน้า dashboard อีกชุด แนะนำขยายเฉพาะเมื่อมีไฟล์ค้าง หลังลบคำตอบต้องยังมีรหัสอ้างอิงติดตามจากผลลบ/metadata ที่เก็บไว้ ไม่ทำให้ข้อมูลคำตอบที่ลบกลับมาเป็นรายการปกติ

นี่เป็นข้อเสนอการวาง controls และข้อมูล ไม่ใช่ resolution ยังไม่เขียนโค้ดเพิ่ม เปิดเดโม หรือเรียก ECM/DB และยังไม่ถือว่าผู้ใช้เลือกทางใดแล้ว

### Resolution — 2026-11-13 — ยืนยันร่วมกับผู้ใช้

ผู้ใช้เลือก **ใช้กล่องเดิมของปุ่ม PoC**, **ข้อความค้างในหน้าเดิม** และ **ขยายรายละเอียดในหน้าเดิม** ครบทั้งสามคำถาม ข้อสรุปนี้แทน frontier ที่รอคำตอบและสถานะรอหารือในบันทึกก่อนหน้า เป็นการตัดสินแผน UI ไม่ใช่การอนุญาตให้เริ่มพัฒนาหรือเรียก ECM จริง

#### ฐานของงานและการตั้งค่าของ Admin

- ต่อจากปุ่ม PoC ในชีตและแผงตั้งค่า Field เดิม ไม่สร้างหน้า upload/editor ใหม่ ไม่ใช้โค้ดเดโมแยกเป็นฐาน และไม่ต้องเลือกหนึ่งในสาม layout ของเดโมที่ยกเลิกแล้ว
- เพิ่ม Document Category ของช่องแนบในแผงตั้งค่าเดิม ใช้รายการ API และค่าที่บันทึกตาม [นโยบาย Admin](03-admin-storage-policy.md) Tag อัตโนมัติ/การแก้ชื่อ/required ใช้กติกาและ controls เดิม พร้อมรักษา binding ที่ตรวจแล้ว หมวดของคอลัมน์ใช้ร่วมทุกแถว
- แสดงความครบถ้วนของ category และ scalar tags ก่อนเผยแพร่ในจุดแจ้งผลเดิม ไม่เพิ่มปี storage หรือบังคับกรอกค่าปี/เลขของ User ในขั้นสร้างต้นแบบ การตั้งค่ายังไม่ครบเก็บ Template Draft ได้ แต่การเผยแพร่ต้องผ่านข้อกำหนดที่ตกลงแล้ว
- API รายการหมวดไม่พร้อมต้องคงค่าที่บันทึกไว้ ไม่เปลี่ยนหมวด ล้างค่า หรือบังคับตรวจสดก่อนเผยแพร่ Published Template ยังคงล็อก; [นโยบายต่อยอด PoC](12-poc-form-cutover.md) และการทำสำเนาสำหรับฟอร์มที่เผยแพร่แล้วไม่เปลี่ยน

#### กล่องเดิมของปุ่มในหน้าแก้ไข

- User แก้ Draft และ Admin แก้ Correction ผ่านปุ่ม PoC ที่ตำแหน่งเดิม แล้วเปิดกล่องเดิมที่เสริมข้อมูล/คำสั่ง ไม่เพิ่มชุด drawing หรือปุ่มจัดการไฟล์ข้าง URL ในชีต
- กล่องแยก **ไฟล์ที่บันทึกแล้ว** ซึ่งมี URL ปัจจุบัน ออกจาก **ไฟล์ที่เพิ่งเลือกและยังไม่บันทึก** ซึ่งแสดงชื่อ/ขนาดจริง การเปิด URL ไม่เริ่ม file picker หรือเปลี่ยนไฟล์
- ใช้คำสั่งเลือก/เปลี่ยนไฟล์ นำไฟล์ออก และยกเลิกการเปลี่ยนในกล่องนี้ การเลือก/นำออกยังไม่ upload/delete ทันที ต้องกดบันทึก/ส่งตาม [วงจรไฟล์](05-safe-draft-lifecycle.md) และห้ามทำไฟล์เดิมหายเมื่อเลือกไฟล์ไม่ผ่านเกณฑ์
- หน้าอ่านแบบ read-only และ export แสดง URL ของฉบับที่เลือกแทนปุ่ม ไม่มี picker หรือคำสั่งเปลี่ยน/นำออก ไม่ฝัง preview ไฟล์แนบและไม่เปลี่ยน viewer ของเอกสารหลัก ตาม [สิทธิ์และประวัติ](06-history-access.md)

#### ข้อความสถานะค้างในหน้าเดิม

- ใช้ข้อความที่ยังเห็นในหน้ากรอกเดิม พร้อมชื่อ Field/ช่อง/แถว สาเหตุ และสิ่งที่ทำต่อ ไม่ใช้เพียง toast ที่หมดเวลา และไม่ใช้ badge ที่ต้องเปิดดูจึงจะรู้ว่าบันทึกไม่ได้
- แยกการเลือกที่ยังไม่บันทึก การบันทึกสำเร็จ การตรวจไม่ผ่าน ผล upload ที่ไม่แน่ชัด ผลบันทึก Folio ที่ต้องตรวจ และการลบไฟล์เก่าค้าง ไม่เรียกทุกกรณีว่า “บันทึกไม่สำเร็จ” หรือแสดง spinner ไม่มีกำหนด
- ไฟล์/metadata ไม่ผ่านต้องระบุจุดแก้ คงข้อมูลที่บันทึกแล้วและ selection ที่ยังรักษาไว้ในหน้าได้ ไม่เงียบแล้วกลับไปใช้ไฟล์เดิมเพื่อข้าม validation; กฎ required/ไฟล์ 0 bytes/แถวที่มีแต่ไฟล์ยังยึด [ข้อกำหนดไฟล์](07-pdf-acceptance.md)
- ไม่ทราบผล upload ให้แจ้งว่าร่างเดิมอ่านได้ แต่บันทึก ส่ง และลบคำตอบนี้ไม่ได้จนผู้ดูแลยืนยันครบ ไม่เสนอ write retry อัตโนมัติ หากไม่ทราบผล Folio ให้ตรวจ operation เดิมก่อน ไม่เริ่ม upload หรือสร้างฉบับซ้ำ
- บันทึกเอกสารกับ JSON แล้วแต่ลบเก่าค้างให้แจ้งผลสองส่วนตามจริง ใช้ข้อมูล/URL ใหม่ต่อได้และเตือนว่า URL เก่าอาจยังเปิดได้ สถานะลบค้างต้องไม่ถูกล้างเพียงเพราะบันทึกรอบถัดไปสำเร็จ
- ECM login ผิดพลาดเป็นข้อผิดพลาดการเชื่อมต่อ ไม่ทำให้ User กรอก credentials ECM หรือถูกออกจาก Folio โดยผิดเหตุ; แยกจาก Folio session ที่ไม่ถูกต้องจริงตาม [แผน auth](13-folio-ecm-auth.md)

#### รายละเอียดติดตามของ Admin

- ขยายส่วนรายละเอียดในหน้าผลลัพธ์เดิมเฉพาะเมื่อมีไฟล์ที่ต้องติดตาม ไม่สร้าง dashboard อีกชุด และไม่เลือกเปิดกล่องรายละเอียดแยกเป็นรูปแบบหลัก
- แสดงเลขอ้างอิงงาน ขอบเขตช่อง/แถว ชื่อฉบับที่วางแผนไว้ ปี category เวลา/ผลที่ server รู้ และผล/หลักฐานการตรวจที่มีสิทธิ์อ่าน ใช้ข้อมูลจาก operational records ที่ตรวจแล้ว ไม่ใช้ข้อความ URL หรือ token ที่กรอกเองเป็นหลักฐานยึดหรือลบไฟล์
- การบันทึกข้อความประสานไม่เท่ากับยืนยันว่าคำขอจบหรือไฟล์ถูกลบแล้ว การปลดค้างต้องผ่านเงื่อนไขผู้ดูแลและหลักฐานใน [วงจรไฟล์](05-safe-draft-lifecycle.md) ไม่เพิ่มสิทธิ์ให้ User/Viewer หรือถือว่าการค้นไม่พบครั้งเดียวเพียงพอ
- เมื่อลบทั้ง Response แล้วแต่ยังมีไฟล์ค้าง ต้องสื่อว่าข้อมูลคำตอบถูกลบแล้วและยังตามไฟล์ไม่ครบ พร้อมรหัสอ้างอิงที่ยังติดตามได้จาก metadata ที่เก็บไว้ ไม่คืนข้อมูลคำตอบที่ลบแล้วเป็นรายการผลลัพธ์ปกติ และไม่ทำให้งานติดตามหายไปเพราะ rows ถูกลบ

#### ขอบเขตการยืนยัน

นี่คือ verdict ผ่านการสนทนาของการเสริม UI เดิม ไม่ใช่การรับรองเดโมหรือ runtime ไม่เปลี่ยนข้อสรุปการบันทึก/JSON/สิทธิ์/ประวัติ/ชื่อไฟล์/การต่อยอด PoC ที่ตั๋วอื่นเป็นเจ้าของ และไม่สร้างศัพท์หรือ ADR ใหม่

ตรวจ source ของแผง Field, กล่อง PoC และ host เพื่อระบุจุดต่อ พร้อมตรวจ tracker/ลิงก์/dependencies เท่านั้น รอบหารือนี้ไม่แก้ application ไม่เปิดเดโม ไม่ใช้ credentials และไม่เรียกหรือทดสอบ ECM, DB, ONLYOFFICE หรือ export จริง เงื่อนไขทดสอบ/บัญชีก่อนเปิดใช้งานยังคงตามตั๋วเจ้าของข้อกำหนด
