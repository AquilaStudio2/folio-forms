# สิทธิ์ไฟล์และการแก้ไขหลังส่งคำตอบ

Labels: wayfinder:grilling Type: grilling Parent: ../map.md Status: resolved Assignee: pyw1tt Blocked by:

## Question

User, Admin และ Viewer ควรเปิด/ดาวน์โหลด/เปลี่ยน/ลบไฟล์ได้ในสถานะใด และเมื่อ User กลับมาแก้เพื่อส่งใหม่หรือ Admin ทำ Correction จะรักษาไฟล์ของ Submission และ revision เก่าอย่างไร?

ตัดสินขอบเขตการเปลี่ยนไฟล์หลังส่ง, การอ้างไฟล์เดิมข้าม revision, การลบ Response/Form และพฤติกรรมของลิงก์หรือสิ่งที่แสดงในผลลัพธ์/ไฟล์ export โดยไม่ทำให้การดู revision เก่าอ่านไฟล์ผิดฉบับ ต้องรักษาขอบเขตข้อมูล User และไม่เปิด token/credentials ให้ browser

ขอบเขตนี้รวมผลกระทบหลังส่งแล้ว แต่ไม่ได้สรุปว่าต้องอนุญาตการเปลี่ยนไฟล์ทุกกรณี ใช้ CONTEXT.md เป็นฐานสิทธิ์และความหมาย Submission/Correction ปัจจุบัน

## Comments

### 2026-11-12 — Claim

เริ่มหารือเรื่องสิทธิ์ไฟล์และการรักษาไฟล์ตาม Submission/Correction โดย pyw1tt ร่วมกับ agent ขอบเขตเป็นการวางแผนเท่านั้น ยังไม่มีข้อยุติใหม่และไม่อนุญาตให้แก้โค้ดหรือข้อมูลจริง

### 2026-11-12 — หลักฐานใหม่จากงานยืนยันสัญญา ECM

ก่อนสรุปสิทธิ์การเปิดไฟล์ ให้อ่านคำตอบใน [ยืนยันสัญญา ECM ที่เอกสารยังไม่ตอบ](09-provider-contract-evidence.md): ผู้ใช้ระบุว่า file URL เป็น public ไม่ต้องยืนยันตัวตนและไม่มีวันหมดอายุ การซ่อน URL หรือวาง download proxy ใน Folio เพียงอย่างเดียวไม่ทำให้ URL ต้นทางบังคับสิทธิ์ตาม User/Admin/Viewer ได้ ประเด็นนี้ยังต้องหารือใน ticket นี้ ไม่ได้อนุมัติให้เผยแพร่ไฟล์สาธารณะหรือเปลี่ยนนโยบายสิทธิ์เดิม

### Resume — 2026-11-12 — ดำเนินต่อโดยผู้รับผิดชอบเดิม

ผู้ใช้สั่งให้คุยหัวข้อนี้ต่อโดยคงผู้รับผิดชอบ `pyw1tt` และพักการเลือกแนวทาง ECM login ตาม [งานที่รอทีม](10-shared-ecm-login.md) ไม่รอหัวข้อนั้นเพื่อหารือนโยบายสิทธิ์และไฟล์ประวัติ และไม่ถือว่าการเริ่มงานนี้อนุมัติแนวทาง login ใด

เริ่มจากสิทธิ์ปัจจุบันใน CONTEXT.md และข้อจำกัด public URL ที่ผู้ใช้ยืนยันแล้ว การเพิ่มปุ่มดาวน์โหลดที่ตรวจสิทธิ์ใน Folio ไม่ใช่ข้อรับรองว่าจะป้องกันการเปิด URL ต้นทางจากภายนอกได้

### Source evidence — 2026-11-12 — สิทธิ์และผลลัพธ์เดิม

- [canReadSubmission](../../../apps/server/src/responses/query.ts) lines 320–329 ให้ Admin/Viewer อ่านได้ และ User อ่านได้เฉพาะ Submission ของตน; `selectedSubmissionRevision` lines 366–394 เลือกข้อมูล/เอกสารตาม revision ที่ระบุ ไม่แทนด้วย latest เสมอ
- [requireResponseWriter](../../../apps/server/src/auth/identity.ts) lines 112–115 ปฏิเสธ Viewer ที่จะเขียน; [saveCorrection](../../../apps/server/src/routes/results.ts) lines 74–143 กำหนด Admin และ Response ที่กำลัง submitted พร้อม editor authorization/lease
- [routes/responses.ts](../../../apps/server/src/routes/responses.ts) lines 404–475 มีการลบทั้ง Response ของ Admin ที่ต้อง confirm และการ discard ของผู้เขียน; [deleteResponseData](../../../apps/server/src/responses/deletion.ts) lines 122–127 จำกัดผู้ไม่ใช่ Admin ให้ลบได้เฉพาะ Draft ของตน และ lines 351–356 ลบ Correction/Submission/Response ไม่ใช่เพียงย้อนการแก้ในร่าง
- [routes/form-catalog.ts](../../../apps/server/src/routes/form-catalog.ts) lines 397–435 ให้ Admin ลบได้เฉพาะ Form Draft ที่ยังไม่เผยแพร่ ไม่ควรเพิ่มสิทธิ์ลบ Published Form เพื่อจัดการไฟล์แนบ
- ยึด [เกณฑ์รับไฟล์](07-pdf-acceptance.md) ที่ดาวน์โหลดไฟล์แนบอย่างเดียว และ [กติกาชื่อไฟล์](04-confirmation-filename.md) ที่แยกฉบับ ไม่สร้าง preview หรือเขียนทับไฟล์ประวัติขึ้นใหม่ในหัวข้อนี้

ทั้งหมดเป็นหลักฐานจาก source ไม่ใช่การทดลองกับไฟล์ ECM จริง และยังไม่ใช่การตัดสินว่าข้อจำกัด public URL ยอมรับได้หรือผู้ใช้อนุมัติสิทธิ์ใหม่แล้ว

### Discussion — 2026-11-12 — ข้อสรุปสิทธิ์รอบแรก

- ผู้ใช้ยอมรับข้อจำกัด URL สาธารณะของ DCM สำหรับขอบเขตไฟล์แนบนี้ ผู้ที่ได้ URL อาจเปิดได้โดยไม่ login ไม่ถือว่าการควบคุมสิทธิ์ใน Folio ทำให้ไฟล์ต้นทางเป็น private
- สิทธิ์ดาวน์โหลดผ่าน Folio ตามสิทธิ์คำตอบเดิม: User เฉพาะคำตอบของตน, Admin/Viewer ตามสิทธิ์ผลลัพธ์และประวัติเดิม; Viewer แก้หรือลบไม่ได้
- User เปลี่ยน/นำไฟล์ออกได้ใน Draft ของตน หากส่งแล้วต้องกลับมาเป็น Draft ก่อน ไม่แก้ไฟล์ของ Submission เดิมโดยตรง และประวัติเดิมยังอ้างไฟล์ฉบับเดิม
- Admin เพิ่ม/เปลี่ยน/นำไฟล์ออกผ่าน Correction ได้ในสถานะที่ระบบอนุญาต ต้องผ่านกติกาช่องบังคับของ revision ที่จะบันทึกสำเร็จ ไม่แก้ไฟล์ฉบับเก่าและไม่เพิ่มสิทธิ์แก้ Draft ของคนอื่นขึ้นใหม่

#### หลักฐานเพิ่มเติมสำหรับคำถามถัดไป

- [public-forms.ts](../../../apps/server/src/routes/public-forms.ts) lines 261–289 กำหนด `seedFromSubmission` เฉพาะ `form.documentKind !== "xlsx"` เมื่อเริ่มรอบใหม่หลังส่ง Excel จะใช้ Published Template และไม่ seed ข้อมูลจาก Submission เดิม ส่วน Draft ที่ยังมีอยู่ใช้ต่อที่ lines 239–258
- ข้อนี้เป็นข้อยกเว้นของคำอธิบาย Response แบบภาพรวมใน CONTEXT.md ที่กล่าวถึงการ seed จาก Submission จึงยึด source เฉพาะ XLSX สำหรับตัดสินขอบเขตนี้ ไม่สมมติว่าจะคัดไฟล์เก่ามาใส่ตารางว่างได้อย่างถูกแถว และไม่เปลี่ยน flow เริ่มรอบใหม่โดยไม่ตกลงกับผู้ใช้
- การลบ Response ทั้งชุดตาม source ที่อ้างก่อนหน้าเป็นการลบ Submission/Correction ด้วย ต้องแยกคำถามนี้จากการนำไฟล์ออกจากช่องใน Draft/Correction ซึ่งต้องรักษาฉบับเก่าที่ประวัติยังอ้างถึง

### Requirement amendment — 2026-11-12 — URL หลังบันทึกและ tag ของช่องแนบ

ผู้ใช้เพิ่มเติมโดยตรงขณะถามเรื่อง export ข้อกำหนดต่อไปนี้แทนตัวเลือกแสดงชื่อไฟล์อย่างเดียวหรือบังคับดาวน์โหลดในคำถามก่อนหน้า ไม่ต้องถามให้เลือกการแสดง URL ซ้ำ

- เมื่อบันทึกไฟล์แนบสำเร็จ การกลับมาดูคำตอบและเอกสาร Excel/PDF ที่ export ต้องแสดง URL จากผล upload แทนปุ่ม upload เพื่อเปิดเอกสารต้นทาง ใช้ URL ของไฟล์ใน revision ที่กำลังดู ไม่ค้นหา latest ด้วยเลขหนังสือแทน
- ใช้ผล `file_link` ที่ตรวจสัญญาแล้วจากการ upload จริง ไม่สร้าง URL เองจากชื่อ/path และไม่รายงานว่าไฟล์ถูกบันทึกแล้วเพียงเพราะขั้น upload สำเร็จแต่การบันทึกคำตอบ/เอกสารยังไม่ครบ
- หน้าดูแบบอ่านอย่างเดียวและ export ไม่เปิดตัวเลือกอัปโหลดจากปุ่มเดิม หน้าแก้ Draft/Correction ที่มีสิทธิ์ยังต้องมีทางเปลี่ยนหรือนำไฟล์ออกตามสิทธิ์ที่ผู้ใช้ตกลงไว้ โดยแยกการเปิด URL ออกจากการเปลี่ยนไฟล์ ไม่ทำให้การเปิดลิงก์กลายเป็นการแก้เอกสาร
- เก็บ URL และ `file_token` รวมใน JSON คำตอบ ตาม [สัญญาข้อมูลเพิ่มเติม](09-provider-contract-evidence.md) คู่ข้อมูลใน Submission/Correction เก่าต้องไม่เปลี่ยนตามการแทนที่ในร่างใหม่
- การเปิด URL ต้นทางเป็นการใช้ URL สาธารณะตามที่ผู้ใช้ยอมรับ ไม่ใช่ preview ที่ฝังใน Folio และไม่รับรองว่า DCM/browser จะบังคับดาวน์โหลด
- ข้อกำหนด tag อัตโนมัติและการแก้ชื่อโดย Admin อยู่ใน [ระดับการตั้งค่าปลายทางไฟล์ของ Admin](03-admin-storage-policy.md) ไม่ให้ User เปลี่ยน tag หรือสิทธิ์การลบผ่านการแก้ JSON เอง

คำถามเรื่องเริ่มรอบใหม่ของ Excel และการลบไฟล์เมื่อทั้ง Response ถูกลบยังไม่ได้รับคำตอบ เพราะการถามถูกขัดจังหวะด้วยข้อกำหนดใหม่นี้ ไม่ถือว่าผู้ใช้เลือกค่าแนะนำไว้แล้ว หัวข้อนี้ยัง claimed และเรื่อง login ยังคงพักรอทีม

### Discussion — 2026-11-12 — รอบใหม่และการลบทั้งคำตอบ

- ผู้ใช้เลือกคง flow Excel เดิม: เริ่มรอบใหม่หลังส่งจากต้นแบบว่าง ไม่ดึง URL/ไฟล์ของ Submission เก่ามาเติมเอง ส่วนการเปิด Draft ที่ยังไม่ส่งเป็นการใช้ไฟล์/URL ของร่างที่บันทึกไว้นั้นต่อ
- ผู้ใช้เลือกให้การลบ Response ทั้งชุดตามสิทธิ์เดิมลบไฟล์ ECM ที่ Folio อัปโหลดและไม่มีคำตอบ/revision อื่นอ้างถึงแล้วด้วย โดยรับทราบว่าลบ ECM กู้คืนไม่ได้และ URL ที่ส่งต่อจะใช้ไม่ได้หลังไฟล์ถูกลบ
- ต้องตรวจความเป็นเจ้าของและการอ้างอิงจากข้อมูล canonical ฝั่ง server ก่อนใช้ file token ลบ ไม่ค้นหาเลขหนังสือแล้วลบไฟล์ล่าสุด และไม่ใช้การลบทั้งคำตอบเป็นเหตุลบไฟล์ที่คำตอบหรือประวัติอื่นยังใช้อยู่

ยังไม่ถือว่าข้อสรุปนี้เลือกวิธี authentication ของ ECM หรือกำหนดลำดับ cleanup/recovery เอง งานวงจรไฟล์ยังเป็นเจ้าของลำดับทำงานและผลเมื่อลบหรือบันทึกสำเร็จไม่ครบ

### Resolution — 2026-11-12 — ยืนยันร่วมกับผู้ใช้

ผู้ใช้ยืนยันข้อสรุปสิทธิ์ ประวัติ การแสดง URL และการลบแล้ว ข้อสรุปนี้แทนข้อความที่ยังรอคำตอบใน Discussion ก่อนหน้า ไม่ปิดหรือเลือกแนวทาง ECM login ที่รอทีม และไม่อนุญาตให้พัฒนาหรือเปลี่ยนข้อมูลจริง

#### สิทธิ์และความเป็นสาธารณะ

- ใช้สิทธิ์คำตอบเดิมใน Folio: User อ่านได้เฉพาะของตน; Admin/Viewer ตามสิทธิ์ผลลัพธ์และประวัติเดิม; Viewer เปลี่ยนหรือลบไฟล์ไม่ได้ ไม่เพิ่มช่องทางให้ User อ่านหรือจัดการไฟล์ของคนอื่น
- ผู้ใช้ยอมรับ URL สาธารณะของ DCM สำหรับขอบเขตนี้ ผู้ที่ได้ URL อาจเปิดได้โดยไม่ login และไม่มีวันหมดอายุตามข้อมูลที่ได้รับ การซ่อน URL หรือ proxy ไม่ใช่การทำต้นทางให้ private
- ไม่ใช้ ECM credentials/login token เป็นข้อมูลในคำตอบ ลิงก์ export หรือสิทธิ์ของ User

#### การแก้ไฟล์และประวัติ

- User เพิ่ม/แทนที่/นำไฟล์ออกได้ใน Draft ของตน หากส่งแล้วต้องกลับมาเป็น Draft ก่อน ไม่แก้ไฟล์ของ Submission เดิมโดยตรง
- Admin จัดการไฟล์ผ่าน Correction ได้เฉพาะสถานะที่ระบบอนุญาต ใช้เหตุผลและ revision ตามเดิม และต้องผ่านกติกา required ก่อนสร้าง Correction ที่สำเร็จ ไม่เพิ่มสิทธิ์แก้ Draft ของคนอื่นหรือแก้ Submission เก่าโดยตรง
- การเปลี่ยนไฟล์สร้างฉบับใหม่ตาม [กติกาชื่อไฟล์](04-confirmation-filename.md) ประวัติเดิมยังอ้างไฟล์เดิม และการนำไฟล์ออกจากร่าง/revision ใหม่ไม่เป็นเหตุลบไฟล์ที่ประวัติอื่นยังใช้อยู่
- ยึด source ของ Excel ที่เริ่มรอบใหม่หลังส่งจาก Published Template โดยไม่คัดข้อมูล/URL/ไฟล์รอบก่อนมาเอง ต่างจากการเปิด Draft ที่ยังไม่ส่งซึ่งต้องใช้ไฟล์และ URL ที่บันทึกในร่างนั้นต่อ
- คำอธิบาย Response แบบภาพรวมใน CONTEXT.md มีข้อยกเว้น XLSX ตาม source ที่อ้างข้างต้น ต้องคำนึงถึงข้อยกเว้นนี้เมื่อปรับ domain/workflow docs ในขั้นพัฒนา ไม่เปลี่ยน flow เริ่มรอบใหม่เพียงเพื่อให้ไฟล์แนบทำงาน

#### URL ในหน้าดูและเอกสารส่งออก

- หลังบันทึกไฟล์และคำตอบสำเร็จ กลับมาดูคำตอบหรือ export Excel/PDF ต้องแสดง URL จากผล upload แทนปุ่ม upload เพื่อเปิดเอกสาร ไม่แสดงเพียงชื่อไฟล์และไม่สร้าง URL เองจาก path
- ใช้ URL ของช่อง/แถวใน revision ที่กำลังดู ไม่ค้นหาเลขหนังสือแล้วเลือก latest แทน และไม่เปลี่ยนไปเปิดไฟล์คนละฉบับหาก URL เดิมมีปัญหา
- หน้าดูแบบอ่านอย่างเดียวและ export ไม่เปิด file picker หน้าแก้ Draft/Correction ที่มีสิทธิ์ยังต้องมีคำสั่งเปลี่ยน/นำไฟล์ออก โดยไม่ทำให้การเปิดลิงก์เป็นการแก้ไฟล์
- เปิด URL ต้นทาง ไม่ฝัง preview ของไฟล์แนบใน Folio ไม่เปลี่ยน viewer ของ DOCX/XLSX หลัก และไม่รับรองว่าพฤติกรรม browser/DCM จะบังคับดาวน์โหลด
- เก็บ URL และ `file_token` จากผล upload ใน JSON คำตอบตาม [สัญญาข้อมูล](09-provider-contract-evidence.md) ของ Draft/Submission/Correction นั้น ไม่เปลี่ยนคู่ข้อมูลของ revision เก่าตามร่างใหม่
- tag อัตโนมัติและการแก้ชื่อโดย Admin ก่อนเผยแพร่ให้ยึด [ข้อกำหนด Admin](03-admin-storage-policy.md) ไม่เปิดให้ User แก้ tag หรือเลือก file token เอง

#### การลบทั้ง Response

- คงสิทธิ์และ confirmation เดิมของการลบ Response ทั้งชุด ซึ่งรวมประวัติ Submission/Correction ไม่เพิ่มสิทธิ์ลบ Published Form; การ archive ไม่ใช่การลบไฟล์
- เมื่อยืนยันลบทั้งชุด ให้ลบไฟล์ ECM ที่ Folio อัปโหลดและไม่มีคำตอบ/revision อื่นอ้างถึงแล้วด้วย ผู้ใช้รับทราบว่าลบกู้คืนไม่ได้และลิงก์ที่ส่งต่อจะใช้ไม่ได้หลังไฟล์ถูกลบ
- ตรวจความเป็นเจ้าของและการอ้างอิงจากข้อมูล canonical ฝั่ง server ก่อนใช้ file token ลบ ไม่รับ URL/token ที่ client อ้างเองเป็นอำนาจลบ และไม่ลบไฟล์จากผลค้นหา latest หรือไฟล์ของระบบอื่น

#### งานที่ยังเปิด

- [สัญญา JSON ของไฟล์แนบและ URL ใน Excel](11-attachment-json-contract.md) เป็นเจ้าของ representation และการแปลงค่าเอกสาร/metadata โดยรักษา validation เดิม หัวข้อนี้ระบุความต้องการ ไม่อ้างว่า schema ปัจจุบันรองรับแล้ว
- [วงจรไฟล์ร่างและการบันทึกโดยไม่สูญหาย](05-safe-draft-lifecycle.md) เป็นเจ้าของลำดับ upload/save/reference/delete ผลสำเร็จบางช่อง และการเก็บข้อมูล cleanup ให้ยังลบได้อย่างถูกต้องเมื่อคำตอบถูกลบแล้ว
- [การใช้บัญชี ECM ร่วมโดยไม่ตัด token ของระบบอื่น](10-shared-ecm-login.md) ยังคงรอผู้ใช้ปรึกษาทีม ไม่มีการเลือกแนวทางแทน

ตรวจ source ประกอบการตัดสินใจเท่านั้น ไม่ได้เรียก ECM จริง ไม่แก้ application/DB ไม่ทดสอบ upload/export/การลบจริง และไม่อ้างว่า PoC ทำข้อกำหนดเหล่านี้แล้ว
