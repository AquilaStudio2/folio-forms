# แหล่งเลขที่หนังสือยืนยันและกติกาชื่อไฟล์

Labels: wayfinder:grilling Type: grilling Parent: ../map.md Status: resolved Assignee: pyw1tt Blocked by: 02, 03

## Question

เมื่อเลขที่หนังสือยืนยันต้องอ่านจาก tag `docs_number` และชื่อไฟล์ประกอบจากค่านั้นกับชื่อ Document Category ที่ Admin เลือก จะผูกค่าให้ถูกช่อง/แถวและตั้งชื่ออย่างไรโดยไม่เขียนทับไฟล์ของคำตอบหรือประวัติอื่น? ใช้ค่าระดับ Response หรือรายแถว และคงนามสกุลเดิมของไฟล์ทุกชนิดอย่างไร?

ตัดสินกรณี `docs_number` หรือ `fiscal_year` ยังไม่มีตอน Save Draft, ผู้ใช้เปลี่ยนเลข/ปี/แถวโดยยังแนบไฟล์เดิม, หลายช่องหรือหลายแถวชื่อชน, หลาย User/หลาย Form ใช้เลขเดียวกัน และอักขระที่ไม่ปลอดภัยต่อชื่อไฟล์ ระบุว่าอะไรแก้ได้โดยใครและตอนไหน แยกชื่อที่ผู้ใช้เห็นออกจาก file identity ตามความสามารถจริงของ API

แหล่งเลขจาก tag และส่วนประกอบชื่อได้รับคำตอบใน [ยืนยันสัญญา ECM ที่เอกสารยังไม่ตอบ](09-provider-contract-evidence.md) แล้ว ไม่ดึงเลขจากชื่อโครงการโดยอนุมานเอง ยังไม่อนุมัติรูปแบบตัวคั่น การเติมรหัส/รุ่นท้ายชื่อ หรือวิธีเก็บฉบับเก่าเป็นพิเศษ

## Prerequisites

- [โครงสร้าง DCM และการตั้งชื่อไฟล์ที่ Ongoing ใช้จริง](02-dcm-ongoing-flow.md)
- [ระดับการตั้งค่าปลายทางไฟล์ของ Admin](03-admin-storage-policy.md)

## Current constraints

- [ADR 0003](../../../docs/adr/0003-pdms-project-name-choices.md) กำหนดให้ PDMS Project Name Source เก็บเพียงชื่อและรวมชื่อซ้ำเป็นตัวเลือกเดียว จึงกู้ identity ของโครงการจากชื่อที่บันทึกไว้ไม่ได้
- [loadPdmsProjectNames](../../../apps/server/src/pdms/projects.ts) อ่าน `confirmation_document_number` จาก upstream แต่คืนเฉพาะชื่อที่ไม่ซ้ำ (lines 18–25, 86–93) การมีเลขใน API ไม่ได้หมายความว่า Response ปัจจุบันผูกเลขนั้นไว้อย่างถูกต้อง
- ถ้าข้อเสนอจะใช้การเลือกโครงการเพื่อกำหนดเลขหนังสือ ต้องกำหนด identity contract ใหม่โดยรับรู้ trade-off ใน ADR 0003 ไม่จับคู่ชื่อย้อนกลับโดยสมมติว่าไม่ซ้ำ และไม่แก้ ADR เดิมโดยเงียบ ๆ
- ผู้ใช้ยืนยันว่าชื่อซ้ำเขียนทับและอ่านฉบับเก่าไม่ได้ การใช้ชื่อจากเลขหนังสือกับ category เพียงสองส่วนจึงยังไม่รับรองการรักษาประวัติหรือป้องกันชนกัน ต้องตัดสินข้อขัดแย้งนี้ก่อนเลือกวงจรแทนที่ไฟล์ ไม่แก้ด้วยการอัปโหลดก่อนลบอย่างเดียว

## Comments

### Claim — 2026-11-12 — pyw1tt

เริ่มหารือขอบเขต tag `docs_number` รูปแบบชื่อไฟล์และการรักษาฉบับเก่า โดยยึดผลหัวข้อ Admin ที่ใช้ scalar `fiscal_year` หนึ่งค่าต่อ Response และ category รายช่อง/คอลัมน์ ไม่ตัดสินเรื่องปีหรือการเลือก category ซ้ำ ขอบเขตเป็นการวางแผน ไม่แก้ application หรือเรียก ECM จริง

### Discussion — 2026-11-12 — ขอบเขตเลขหนังสือและส่วนประกอบชื่อ

- ผู้ใช้เลือกให้ `docs_number` เป็น scalar Field หนึ่งค่าต่อ Response ทุกช่องและทุกแถวใช้เลขหนังสือเดียวกัน ไม่ใช้เลขแยกรายแถว
- User กรอกหรือเลือกเลขหนังสือตามกติกา Field ที่ Admin กำหนด ไม่ดึงเลขย้อนจากชื่อโครงการโดยอนุมาน
- ผู้ใช้อนุญาตรหัสเฉพาะต่อฉบับเพื่อแยกไฟล์ใหม่จากไฟล์เก่า แต่กำหนดให้ category อยู่ท้ายสุดของชื่อ รูปแบบที่นำมาหารือต่อคือ `<docs_number>-<รหัสเฉพาะฉบับ>-<category>.<นามสกุลเดิม>` โดย category เป็นส่วนท้ายของชื่อก่อนนามสกุล หากไม่มีนามสกุล ชื่อจบที่ category
- รหัสต้องแยกฉบับไฟล์ ไม่ใช้เพียงเลขแถวหรือชื่อช่องที่ยังอาจชนกันระหว่าง User/Form/ฉบับ ไม่ถือว่าการบันทึกซ้ำที่ไม่ได้เปลี่ยนไฟล์ต้องสร้างรหัสและอัปโหลดใหม่

ยังต้องตกลงกรณี metadata ว่าง/ไม่ถูกต้อง การเปลี่ยนเลขหรือปีหลังมีไฟล์ที่บันทึกไว้ และการจัดการอักขระในชื่อไฟล์ จึงยังไม่ปิด ticket

### Discussion — 2026-11-12 — Metadata และการใช้ไฟล์เดิม

- User เลือกไฟล์ก่อนกรอกเลข/ปีได้ แต่หากมีไฟล์ที่จะอัปโหลดและ `docs_number` หรือ `fiscal_year` ว่าง/ไม่ถูกต้อง ต้องหยุด Save/Submit ก่อนอัปโหลดและแจ้ง Field ที่ต้องแก้ ไม่ล้างไฟล์ที่เลือกหรือรายงานว่าเก็บไฟล์แล้ว
- เมื่อ User เปลี่ยน `docs_number` หรือ `fiscal_year` หลังบันทึกไฟล์ร่าง ให้ระบบอ่านไฟล์ที่บันทึกไว้และอัปโหลดเป็นฉบับใหม่ตาม metadata ใหม่ ไม่บังคับให้ User เลือกไฟล์เดิมอีกครั้ง ต้องคงไฟล์เดิมจนเปลี่ยนสำเร็จ และไม่แก้ไฟล์ประวัติเดิม
- ผู้ใช้เลือกปฏิเสธอักขระที่ไม่ปลอดภัยในชื่อไฟล์ ไม่แทนด้วย `_` และไม่แก้ชื่อโดยเงียบ ๆ หากเลขหนังสือจริงมี `/` หรือ `\` ข้อนี้ทำให้ยังใช้ค่านั้นแนบไม่ได้ ต้องแก้ข้อมูลก่อน หากต้นเหตุเป็น category ต้องแก้ผ่านผู้มีสิทธิ์ตั้งค่า category ไม่เปิดให้ User เปลี่ยนหมวดเอง
- ต้นแบบที่มีปุ่มแนบต้องมี scalar Field tag `docs_number` ก่อนเผยแพร่ แต่ไม่ต้องมีค่าหนังสือของ User ตั้งแต่ขั้นออกแบบ Template Draft ยังบันทึกการตั้งค่าที่ยังไม่ครบได้

ยังไม่ถือว่าการเลือกใช้ไฟล์เดิมเป็นหลักฐานว่าอ่านไฟล์ต้นทางหรืออัปโหลดซ้ำได้จริง ต้องรักษาข้อจำกัดของหลักฐานและเส้นทางล้มเหลวในการพัฒนา งานวงจรไฟล์เป็นเจ้าของวิธีเปลี่ยน references/ลบไฟล์ร่างเก่าเมื่อสำเร็จและการกู้คืนเมื่อไม่สำเร็จ

### Resolution — 2026-11-12 — ยืนยันร่วมกับผู้ใช้

ผู้ใช้ยืนยันข้อสรุปหลังรับทราบผลของการปฏิเสธอักขระในชื่อไฟล์แล้ว คำตอบในส่วนนี้เป็นฉบับสุดท้ายของหัวข้อ แทนสถานะที่ยังรอตัดสินใน Discussion ก่อนหน้า ไม่ใช่การอนุมัติให้พัฒนาหรือเรียก ECM จริง

#### แหล่งเลขหนังสือและเงื่อนไขต้นแบบ

- `docs_number` เป็น scalar Field หนึ่งค่าต่อ Response ทุกช่องแนบและทุกแถวในตารางใช้เลขเดียวกัน ไม่ใช้เลขแยกรายแถว และไม่ย้อนหาเลขจากชื่อโครงการ
- User กรอกหรือเลือก `docs_number` ตามกติกา Field ที่ Admin กำหนด เช่นเดียวกับ `fiscal_year` ที่ตกลงไว้ใน [ระดับการตั้งค่าปลายทางไฟล์ของ Admin](03-admin-storage-policy.md)
- ต้นแบบที่มีปุ่มแนบต้องมี scalar Field tag `docs_number` ก่อนเผยแพร่ เช่นเดียวกับ `fiscal_year` แต่ไม่ต้องมีค่าของ User ในขั้นออกแบบ Template Draft ที่ยังตั้งค่าไม่ครบยังบันทึกได้
- การรับค่าเลขหนังสือไม่เพิ่มข้อบังคับรูปแบบ `กทอ.` ตาม Ongoing โดยอัตโนมัติ ใช้กติกา Field และสัญญา ECM ร่วมกับข้อกำหนดความปลอดภัยของชื่อไฟล์

#### รูปแบบชื่อและ identity

ใช้ `<docs_number>-<รหัสเฉพาะฉบับ>-<category>.<นามสกุลเดิม>` โดย category เป็นส่วนท้ายของชื่อก่อนนามสกุล หากไฟล์ไม่มีนามสกุล ให้ชื่อจบที่ category ไม่เติม `.pdf` หรือเปลี่ยนเนื้อหา/ชนิดไฟล์

- category มาจากค่าที่ Admin เลือกและบันทึกไว้ตาม [สัญญา ECM ที่ยืนยันแล้ว](09-provider-contract-evidence.md) ไม่ให้ User กำหนดหมวดหรือเปลี่ยนชื่อหมวดเอง
- รหัสเฉพาะแยกไฟล์ที่อัปโหลดแต่ละฉบับ รวมกรณีต่างช่อง/แถว/User/Form เพื่อไม่ใช้ชื่อเดิมเขียนทับไฟล์ที่มีอยู่ รหัสไม่ใช่เพียงเลขแถวหรือชื่อ binding ที่ซ้ำข้ามคำตอบได้
- เมื่อมีไฟล์ใหม่หรือมีการอัปโหลดไฟล์เดิมด้วย metadata ใหม่ ให้สร้าง identity/ชื่อของฉบับใหม่ ไม่เปลี่ยน bytes หรือทำให้ลิงก์ของฉบับประวัติอ่านไฟล์ใหม่แทน
- การบันทึกซ้ำที่ไฟล์และ metadata ไม่เปลี่ยน ไม่ต้องสร้างฉบับหรืออัปโหลดใหม่เพียงเพราะกด Save/Submit
- ใช้ตัวอ้างอิงของไฟล์ที่บันทึกสำเร็จจริงกับช่อง/แถวและ revision ที่เกี่ยวข้อง ไม่ใช้การค้นหาเลขหนังสือแล้วเลือกไฟล์ล่าสุดแทน identity ของไฟล์

#### ค่าว่างหรือไม่ถูกต้อง

- User เลือกไฟล์ไว้ก่อนได้ หากมีไฟล์ที่จะอัปโหลดแต่เลขหนังสือหรือปีว่าง/ไม่ถูกต้อง ให้หยุด Save/Submit ก่อนอัปโหลด แจ้ง Field ที่ต้องแก้ และคงไฟล์ที่เลือกไว้ในหน้า ไม่ใช้เลขหรือปีสมมติ และไม่รายงานว่าเก็บไฟล์แล้ว
- การคงไฟล์ไว้ในหน้าไม่ได้หมายความว่าไฟล์ถูกบันทึกถาวรหรือจะอยู่หลัง reload/ออกจากหน้า
- ปฏิเสธชื่อที่มีอักขระไม่ปลอดภัย ไม่แทนด้วย `_` ไม่ตัด/เปลี่ยนค่าโดยเงียบ ๆ และไม่แก้ค่าจริงใน tags เพื่อให้ผ่าน
- ผลที่ผู้ใช้รับทราบคือเลขหนังสือจริงที่มี `/` หรือ `\` จะยังใช้แนบไฟล์ไม่ได้ตามกติกานี้ หากอักขระที่ใช้ไม่ได้มาจาก category ให้แจ้ง Admin/ผู้ดูแลหมวด ไม่เปิดให้ User เปลี่ยน category เองหรือหลบกติกาล็อกหลังเผยแพร่
- เมื่อยังไม่มีไฟล์ต้องอัปโหลด กฎนี้ไม่เพิ่มข้อบังคับให้ Draft ที่ยังกรอกไม่ครบต้องมีเลข/ปีเสมอ การตรวจ Field และเงื่อนไข Submit ปกติยังคงเดิม

#### การเปลี่ยนเลขหรือปีหลังมีไฟล์ร่าง

- เมื่อ User เปลี่ยน `docs_number` หรือ `fiscal_year` ให้ระบบอ่านไฟล์ที่บันทึกไว้และอัปโหลดเป็นฉบับใหม่ด้วย metadata ใหม่เมื่อกด Save Draft หรือ Submit เท่านั้น ไม่เริ่มอัปโหลดเพราะแก้ค่า Field
- ใช้ปีและเลขปัจจุบันของคำตอบเดียวกันกับไฟล์ทุกช่องในร่างที่ได้รับผล หาก User เลือกไฟล์ทดแทนในช่องนั้นอยู่แล้ว ใช้ไฟล์ที่เลือกใหม่ ไม่ดึงไฟล์เก่ามาแทนการเลือกของ User
- คงไฟล์เดิมจนการเปลี่ยนสำเร็จ หากอ่านไฟล์เดิมหรืออัปโหลดใหม่ไม่ได้ ห้ามทำให้ไฟล์เดิมสูญหายหรือรายงานว่าการเปลี่ยนสำเร็จ
- ไม่เขียนทับ ย้าย หรือเปลี่ยนชื่อไฟล์ที่ Submission/Correction เก่ายังอ้างถึง ข้อนี้ไม่เพิ่มสิทธิ์แก้เลข/ปีของ revision ที่เดิมแก้ไม่ได้

#### ขอบเขตที่ยังไม่ตัดสินและหลักฐานที่ยังไม่ทดสอบ

- [วงจรไฟล์ร่างและการบันทึกโดยไม่สูญหาย](05-safe-draft-lifecycle.md) เป็นเจ้าของลำดับอัปโหลด/บันทึก references/ลบไฟล์ร่างเก่าที่ไม่มีประวัติใช้อยู่ ผลสำเร็จบางช่อง กรณี response หาย และการกู้คืน ไม่ถือว่าการมีรหัสฉบับแทนคำตอบเรื่อง lifecycle ทั้งหมดแล้ว
- [สิทธิ์ไฟล์และการแก้ไขหลังส่งคำตอบ](06-history-access.md) ยังเป็นเจ้าของสิทธิ์ในแต่ละสถานะ การแก้หลังส่ง และ Correction หัวข้อนี้ไม่ปิดงานนั้นแทน
- ชื่อไฟล์ใหม่ไม่ทำให้ URL public กลายเป็น private และไม่แก้ปัญหา token ของบัญชี ECM ที่ใช้ร่วมกัน
- การใช้ไฟล์เดิมอัปโหลดใหม่เป็นความต้องการที่ผู้ใช้เลือก ไม่ใช่หลักฐาน runtime ว่าดึง bytes หรืออัปโหลดซ้ำสำเร็จ ไม่รับรองขนาด/ชนิดไฟล์หรือ response นอกสิ่งที่เอกสารและคำชี้แจงรองรับ

ไม่ได้ login/download/upload/delete กับ ECM จริง ไม่แก้ application/DB ไม่เปลี่ยน ADR และไม่สร้างรูปแบบบังคับเลขหนังสือจากชื่อหรือพฤติกรรม Ongoing
