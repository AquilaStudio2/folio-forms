# ปุ่มดาวน์โหลดในแถว Document / Fields ของหน้าผลลัพธ์

Status: ready-for-agent

## Problem Statement

Admin และ Viewer ที่เปิดหน้าผลลัพธ์ `/admin/results/:responseId` ต้องเลื่อนสายตาออกจากบริเวณ Document / Fields ไปหาปุ่มส่งออกในการ์ดด้านบน ทำให้คำสั่งดาวน์โหลดแยกจากข้อมูลที่กำลังตรวจอยู่ และชื่อปุ่มยังไม่สอดคล้องกับปุ่มดาวน์โหลดที่คุ้นเคยจากหน้ากรอก Form

ผู้ใช้ต้องการปุ่มดาวน์โหลดสองปุ่มในบริเวณเดียวกับแท็บตามภาพอ้างอิง โดยแสดงเฉพาะเมื่อ Response ปัจจุบันอยู่ในสถานะ “ส่งแล้ว” และไฟล์ที่ได้ต้องตรงกับรุ่นข้อมูลที่กำลังเลือกดู

## Solution

ย้ายปุ่มส่งออกเดิมมาไว้ด้านขวาของแถว Document / Fields ไม่เพิ่มชุดปุ่มซ้ำ และให้ใช้งานได้จากทั้งสองแท็บ บนจอแคบให้กลุ่มปุ่มตัดบรรทัดโดยไม่ล้นแนวนอน

- XLSX Form แสดง “ดาวน์โหลด Excel” และ “ดาวน์โหลด PDF”
- DOCX Form แสดง “ดาวน์โหลด DOCX” และ “ดาวน์โหลด PDF”
- แสดงปุ่มเฉพาะ Response ที่ปัจจุบันเป็น submitted ไม่ใช่อิงสถานะเผยแพร่ของ Form หรือการเคยมี Submission
- ดาวน์โหลดเอกสารที่บันทึกแล้วของ Submission และ Revision ที่เลือก รวมถึง Original และ Correction เก่า ไม่บังคับเป็นรุ่นล่าสุด
- คงสิทธิ์ Admin และ Viewer รวมถึงการป้องกันคำขอซ้ำและการแจ้งข้อผิดพลาดเดิม

Revision selector และปุ่มเปิด Correction อยู่ตำแหน่งเดิม การดาวน์โหลดไม่บันทึก Draft ไม่ส่งคำตอบ และไม่แก้ข้อมูลที่จัดเก็บ

## User Stories

1. ในฐานะ Admin ฉันต้องการเห็นปุ่มดาวน์โหลดใกล้แท็บผลลัพธ์ เพื่อรับไฟล์จากบริเวณที่กำลังตรวจข้อมูล
2. ในฐานะ Viewer ฉันต้องการใช้ปุ่มดาวน์โหลดในตำแหน่งเดียวกับ Admin เพื่ออ่านและรับสำเนาตามสิทธิ์เดิม
3. ในฐานะ Admin ฉันต้องการเห็นปุ่มส่งออกเพียงชุดเดียว เพื่อไม่ต้องตัดสินใจระหว่างคำสั่งที่ซ้ำกัน
4. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการเห็น “ดาวน์โหลด Excel” สำหรับ XLSX Form เพื่อรู้ว่าจะได้รับสมุดงาน Excel
5. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการดาวน์โหลด XLSX ที่มีคำตอบและรูปแบบเอกสารที่บันทึกแล้ว เพื่อใช้ตรวจหรือส่งต่อ
6. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการเห็น “ดาวน์โหลด DOCX” สำหรับ DOCX Form เพื่อรับไฟล์ชนิดเดียวกับเอกสารต้นฉบับ
7. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการไม่เห็นคำสั่ง Excel บน DOCX Form เพื่อไม่คาดหวังการแปลงไฟล์ที่ระบบไม่ได้ให้บริการ
8. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการดาวน์โหลด PDF จาก XLSX Form เพื่อรับสำเนาเอกสารสำหรับอ่านหรือส่งต่อ
9. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการดาวน์โหลด PDF จาก DOCX Form เพื่อรับสำเนาเอกสารสำหรับอ่านหรือส่งต่อ
10. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการเห็นปุ่มดาวน์โหลดเฉพาะเมื่อ Response ปัจจุบันส่งแล้ว เพื่อไม่เข้าใจว่า Draft เป็นผลลัพธ์ที่ส่งสำเร็จ
11. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการไม่เห็นปุ่มดาวน์โหลดเมื่อ Response กลับมาเป็น Draft แม้เคยส่งแล้ว เพื่อให้คำสั่งตรงกับสถานะปัจจุบัน
12. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการให้การแสดงปุ่มไม่ขึ้นกับสถานะเผยแพร่ของ Form เพียงอย่างเดียว เพื่อไม่สับสนระหว่างสถานะแบบฟอร์มกับสถานะคำตอบ
13. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการดาวน์โหลด Original ที่เลือกดู เพื่อรับหลักฐานของ Submission ก่อนมี Correction
14. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการดาวน์โหลด Correction เก่าที่เลือกดู เพื่อรับเอกสารของรุ่นนั้นแทนรุ่นล่าสุด
15. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการให้เอกสารต้นฉบับและ PDF ใช้ Revision เดียวกับข้อมูลที่แสดง เพื่อเปรียบเทียบเนื้อหาได้ถูกต้อง
16. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการให้การเปิดหน้าเลือก Revision เริ่มต้นตามพฤติกรรมเดิม เพื่อไม่เปลี่ยนวิธีตรวจงานที่ใช้อยู่
17. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการดาวน์โหลดขณะอยู่ในแท็บ Document เพื่อรับเอกสารที่กำลังอ่าน
18. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการดาวน์โหลดขณะอยู่ในแท็บ Fields เพื่อรับเอกสารโดยไม่ต้องสลับกลับไปอีกแท็บ
19. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการให้ปุ่มยังใช้งานไม่ได้เมื่อประวัติรุ่นยังไม่พร้อมหรือโหลดล้มเหลว เพื่อไม่ส่งออกจากรุ่นที่ยังยืนยันไม่ได้
20. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการให้ระบบกันการกดดาวน์โหลดซ้ำระหว่างทำงาน เพื่อไม่สร้างคำขอไฟล์ซ้ำโดยไม่ตั้งใจ
21. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการเห็นข้อผิดพลาดเมื่อส่งออกไม่สำเร็จ เพื่อรู้ว่ายังไม่ได้รับไฟล์
22. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการกดดาวน์โหลดใหม่ได้หลังคำขอล้มเหลว เพื่อรับไฟล์โดยไม่ต้องเริ่มตรวจข้อมูลใหม่
23. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการให้ความล้มเหลวของ PDF ไม่ย้อนสถานะ Submission เพื่อรักษาผลที่ส่งสำเร็จแล้ว
24. ในฐานะผู้ตรวจผลลัพธ์ ฉันต้องการให้การดาวน์โหลดไม่บันทึกหรือแก้คำตอบ เพื่อรับสำเนาโดยไม่เปลี่ยนข้อมูลต้นทาง
25. ในฐานะผู้ตรวจผลลัพธ์บนจอแคบ ฉันต้องการให้แท็บและปุ่มตัดบรรทัดได้ เพื่อเข้าถึงทุกคำสั่งโดยไม่เลื่อนแนวนอน
26. ในฐานะผู้ใช้คีย์บอร์ด ฉันต้องการเข้าถึงและกดปุ่มดาวน์โหลดด้วยคีย์บอร์ด เพื่อไม่ต้องใช้เมาส์
27. ในฐานะผู้ใช้คีย์บอร์ด ฉันต้องการให้ปุ่มลูกศรยังสลับ Document / Fields ตามเดิม เพื่อใช้แท็บได้โดยไม่ถูกรบกวนจากปุ่มดาวน์โหลด
28. ในฐานะ Admin ฉันต้องการให้ Revision selector และปุ่ม Correction ยังอยู่ตำแหน่งเดิม เพื่อคงขั้นตอนตรวจและแก้ผลลัพธ์
29. ในฐานะ Viewer ฉันต้องการดาวน์โหลดได้โดยไม่ได้รับคำสั่ง Correction หรือลบคำตอบ เพื่อคงขอบเขตสิทธิ์อ่านอย่างเดียว
30. ในฐานะ Admin ที่เปิดหน้ารายละเอียด Submission อีกหน้า ฉันต้องการให้แท็บและปุ่มเดิมยังทำงาน เพื่อไม่ให้การปรับ component กลางเปลี่ยนหน้านั้นโดยไม่ได้ตั้งใจ

## Implementation Decisions

- ปรับเฉพาะโมดูลหน้ารายละเอียด Results, component กลางสำหรับแสดงผล Submission, regression ที่เกี่ยวข้อง และคำอธิบายในคู่มือระบบ
- ใช้ Button กลางที่มีอยู่ โดยใช้รูปแบบ secondary ขนาดเล็กตามหน้า fill ไม่สร้าง component ชุดปุ่มส่งออกใหม่ และไม่เพิ่ม dependency
- เพิ่มช่องรับ actions แบบ optional ให้ component แสดงผลกลาง ผู้เรียกที่ไม่ได้ส่ง actions ต้องคงพฤติกรรมเดิม
- component กลางรับผิดชอบเฉพาะ layout แถวหัวและแท็บ ไม่รับผิดชอบกติกาสถานะ สิทธิ์ การเลือก Submission หรือคำขอส่งออก
- แยกกลุ่ม actions ออกจากกลุ่มแท็บในโครงสร้าง accessibility ปุ่มดาวน์โหลดไม่เป็นสมาชิกของ tablist และไม่เปลี่ยน ARIA หรือการควบคุมแท็บด้วยปุ่มลูกศรเดิม
- โมดูลหน้ารายละเอียด Results เป็นผู้ตัดสินใจแสดง actions เฉพาะสถานะ submitted และย้ายปุ่มเดิมออกจากการ์ดบน ไม่คงปุ่มสองตำแหน่ง
- ใช้ชนิดเอกสารของ Form เพื่อเลือก XLSX หรือ DOCX และใช้ PDF เป็นรูปแบบที่สอง ไม่เพิ่มการแปลง DOCX เป็น XLSX
- ใช้ handler ส่งออก สถานะ busy เงื่อนไขปิดปุ่ม และการแจ้งข้อผิดพลาดเดิม ไม่เพิ่มขั้นตอนบันทึกหรือจับสำเนาจาก editor
- ใช้ API ส่งออก Submission เดิม โดยส่ง Submission ID และ Revision ที่เลือกเหมือนเดิม รักษารูปแบบชื่อไฟล์และการตรวจสิทธิ์ ไม่เปลี่ยน API contract หรือ schema
- คงการเลือก Revision เริ่มต้นเดิม ปุ่มส่งออกต้องใช้ Revision เดียวกับข้อมูลที่ผู้ใช้เลือกดู ไม่เปลี่ยนเป็น latest ระหว่างส่งคำขอ
- เมื่อประวัติรุ่นยังไม่พร้อมหรือไม่พบรุ่นที่เลือก ปุ่มยังถูกปิดตามกลไกเดิม เมื่อส่งออกเสร็จหรือล้มเหลวให้ปลด busy ตามกลไกเดิม
- คงการเลือก Revision, คำสั่ง Correction และคำสั่งลบในตำแหน่งและขอบเขตสิทธิ์เดิม รวมถึงการแจ้งข้อผิดพลาดที่มีอยู่
- ทบทวนผู้เรียก component กลางทั้งหน้ารายละเอียด Results และหน้ารายละเอียด Submission ไม่เพิ่ม actions ให้หน้าหลัง
- อัปเดตตารางหน้าและคำอธิบาย Results ในคู่มือระบบพร้อมการเปลี่ยน application จริง ตรวจแผนภาพและอ้างอิงที่เกี่ยวข้อง แล้วสร้างและตรวจ generated outputs ตาม workflow เดิม
- ใช้ความหมาย Response, Draft, Submission และ Correction ตาม domain glossary เดิม ไม่เพิ่มศัพท์หรือ ADR สำหรับการย้าย UI ที่ย้อนกลับได้ง่าย
- ไม่เปลี่ยนกติกาการกรองผลลัพธ์ตาม ADR 0004 การดาวน์โหลดรุ่นเก่าที่ผู้ใช้เลือกไม่เปลี่ยนความหมายของรายการ Results ซึ่งอิงสถานะปัจจุบันของ Response

## Testing Decisions

- ผู้ใช้ยืนยันให้ใช้หน้ารายละเอียด Results เป็น seam หลัก ต่อ integration test UI เดิม และตรวจดาวน์โหลดจริงจากหน้าผ่านเบราว์เซอร์ ไม่เพิ่ม seam ภายใน component
- เทสต์ที่ดีตรวจพฤติกรรมที่ผู้ใช้หรือผู้เรียกภายนอกสังเกตได้ ได้แก่ ความสามารถในการดาวน์โหลด เงื่อนไขสถานะ สิทธิ์ ชนิดไฟล์ รุ่นข้อมูล การป้องกันคำขอซ้ำ และการกู้จากข้อผิดพลาด ไม่ยึดโครงสร้าง props, state ภายใน, class CSS หรือ source text
- ใช้ชุดทดสอบ Viewer access เป็น prior art เพราะเปิด route จริงผ่าน router และมีกรณีอ่าน Correction แล้วดาวน์โหลด PDF ตาม Revision อยู่แล้ว ต่อ fixtures และกรณีทดสอบตรง seam นี้แทนการสร้าง harness ใหม่
- ใช้ข้อมูลสังเคราะห์แยกจากงานจริง ครอบคลุม Admin และ Viewer, XLSX และ DOCX, submitted และ Draft รวม Response ที่เปิด Draft รอบใหม่หลังเคยมี Submission
- ตรวจว่ามีชุดปุ่มเดียวเมื่อส่งแล้ว ไม่มีปุ่มส่งออกเมื่อเป็น Draft และ Viewer ไม่ได้รับคำสั่ง Correction หรือลบคำตอบ
- ตรวจการเลือก Original และ Correction ที่มีค่าต่างกัน แล้วส่งออกชนิดเอกสารต้นฉบับและ PDF จาก Revision ที่เลือก ไม่ตรวจเพียงว่ามีการเรียกฟังก์ชัน
- ตรวจประวัติรุ่นที่ยังโหลดอยู่หรือโหลดล้มเหลว การกดซ้ำระหว่าง busy และการลองใหม่หลังส่งออกล้มเหลว โดยใช้การควบคุม response ตามรูปแบบชุดทดสอบเดิม
- การค้นหาปุ่มด้วย accessible name เป็นส่วนหนึ่งของการทดสอบใช้งาน ไม่สร้างเทสต์เฉพาะยึดข้อความหรือค่าเริ่มต้นที่ไม่เกี่ยวกับพฤติกรรม
- ตรวจผ่านเบราว์เซอร์จริงบนหน้าผลลัพธ์ กดดาวน์โหลดและเปิด XLSX, DOCX และ PDF เพื่อตรวจเนื้อหาที่ต่างกันระหว่าง Original กับ Correction ไม่ถือว่า URL คำขอหรือ mock blob พิสูจน์เนื้อหาไฟล์จริงแล้ว
- ตรวจภาพของแถวปุ่มที่จอกว้างและจอแคบ ตรวจว่าสลับ Document / Fields แล้วยังดาวน์โหลดได้ และใช้ Tab กับปุ่มลูกศรได้ตามหน้าที่เดิม
- ตรวจว่าการส่งออกสำเร็จหรือล้มเหลวไม่เปลี่ยนข้อมูลคำตอบหรือสถานะ Submission การตรวจนี้ใช้ข้อมูลทดสอบและช่องทางอ่านข้อมูลเดิม ไม่เพิ่ม API เพื่อการทดสอบ
- รัน regression ของตารางผลลัพธ์ Spreadsheet ที่มีอยู่ และตรวจหน้ารายละเอียด Submission อีกหน้าผ่าน UI หลังปรับ component กลาง โดยไม่สร้าง unit test ของช่อง actions
- หลังลงมือจริง รันชุด UI ที่เกี่ยวข้องและชุด UI รวม ตรวจ format, lint และ types ตาม scripts เดิม พร้อมสร้างและตรวจคู่มือระบบ เปิด HTML ตรวจคำอธิบาย แผนภาพ ลิงก์ และการซูมที่ได้รับผลกระทบ

## Out of Scope

- เปลี่ยนพฤติกรรมหน้า fill, receipt, ประวัติ Submission หรือหน้ารายละเอียด Submission อีกหน้า
- ดาวน์โหลด Draft จากหน้ารายละเอียด Results หรือเพิ่มสิทธิ์ดาวน์โหลดใหม่
- แปลง Word เป็น Excel หรือเพิ่มชนิดไฟล์ ตัวเลือกพิมพ์ และการส่งออกแบบหลายรายการ
- เปลี่ยนการบันทึก Draft, Submit, Correction, การลบข้อมูล หรือการเลือก Revision เริ่มต้น
- เปลี่ยนผลการกรอง ตารางรายการ Results หรือกติกาใน ADR 0004
- เพิ่ม API, schema, dependency, ระบบส่งออก หรือ abstraction สำหรับการใช้งานในอนาคต

## Further Notes

- ผู้ใช้ยืนยันให้ย้ายปุ่มแทนเพิ่มซ้ำ ใช้ชนิดเอกสารเดิมคู่กับ PDF และดาวน์โหลด Revision ที่เลือก จากนั้นยืนยัน seam การทดสอบตามส่วน Testing Decisions
- Results แสดงสถานะปัจจุบันของ Response การเคยมี Submission ไม่ทำให้ Draft ปัจจุบันมีปุ่มดาวน์โหลด ส่วนการอ่านประวัติ Submission ผ่านหน้าอื่นไม่ถูกเปลี่ยน
- ปุ่มหน้า fill ใช้เป็นตัวอย่างรูปแบบ UI เท่านั้น การดาวน์โหลดจากหน้าผลลัพธ์ใช้เอกสารที่บันทึกแล้ว ไม่ใช้กลไก Excel Fill Download ที่รวมการแก้ไขค้างใน editor
- ตรวจ source และ prior art แล้ว แต่ยังไม่ได้แก้ application source หรือรัน regression ของพฤติกรรมใหม่
- URL ตัวอย่างเปิดแล้วถูกส่งไปหน้า login จึงยังไม่มีหลักฐานจาก session ที่ลงชื่อเข้าใช้หรือไฟล์ดาวน์โหลดจริงของ Form อ้างอิง ต้องตรวจระหว่างการลงมือจริง
- เผยแพร่สเปกนี้ผ่าน Local Markdown ตาม issue tracker ของโครงการ สถานะ ready-for-agent หมายถึงพร้อมนำไปดำเนินการ ไม่ได้หมายความว่าฟีเจอร์ทำเสร็จแล้ว
