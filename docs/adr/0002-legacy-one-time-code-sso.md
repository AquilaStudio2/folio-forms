# ADR 0002: Add a one-time-code bridge for legacy login

**Status:** Accepted

## Context

The old application owns its existing login, including a browser-held access token and refresh cookie. Folio Forms already has its own Users, password login, one-hour sessions, and Form ownership by local User ID. A centralized identity provider and a shared user database are not available. Sending the old token to Folio or linking accounts by matching email would blur the trust boundary and risk assigning a Response to the wrong person.

## Decision

- Add legacy login as an optional path for Folio Users, Viewers and Admins. Keep local password login and Admin-only local account creation; do not enable public password self-registration. PDMS role evidence may grant Folio Admin only through the exact mapping below.
- The old application's same-origin bridge page uses its existing login or refresh helper. Its backend issues a short-lived, single-use code after authenticating the old User. Folio starts a browser-bound transaction, receives the callback, and exchanges the code directly with the old backend using a server-held client credential. Bind the code to the client, exact callback, and PKCE S256 challenge; validate state and pre-login cookie; consume the code atomically. Use HTTPS and do not log credentials or put Folio's session bearer in a URL.
- The configured PDMS backend returns a stable, non-reassignable subject and its authenticated User's stored email, not proof of mailbox ownership. PDMS truthfully returns `email_verified: false`; Folio requires a boolean field and accepts either value from this authenticated exchange. Folio pairs the subject with its configured legacy provider ID and maps the pair to one local User through the existing unique `(providerId, accountId)` Account boundary, rather than matching on email. A first-time identity with a free email is provisioned as an enabled `role=user` account with `emailVerified: false`, `mustChangePassword: false`, and no local credential; its effective role is finalized with the successful SSO session. A safe optional PDMS name is used only during provisioning; otherwise the normalized email is the initial name.
- If the email belongs to an unlinked local User, deny the login and create a Pending Account Link from the authenticated PDMS identity. An Admin reviews the identity evidence and local account ownership, then approves or rejects exactly the displayed review revision. Approval alone grants no access: the User must start a fresh SSO transaction after approval to complete the binding. Changed incomplete email or candidate evidence invalidates approval, returns the request to pending, and requires current review; a candidate's local email change also invalidates pending or approved review, even if restored later. An unresolved request cannot bypass review by changing to a free email; rejected requests remain denied. An existing Admin is eligible for the same reviewed linking process; PDMS privileges do not bypass review. A disabled Folio User stays blocked even if the old login works.
- A completed provider/subject mapping remains authoritative for its current enabled User, Viewer or Admin owner, independent of changed PDMS email or historical review evidence. Keep Folio's name, email, `emailVerified`, credentials, and `mustChangePassword` unchanged on subsequent legacy logins. Retain the immutable review-generation cutoff after linking: a transaction at or before that cutoff is denied even when the mapping exists; a fresh mapped login does not require email equality or renewed approval. A local User with a temporary-password-change requirement may enter through SSO without changing that password; local password login still enforces the change. Keep the two login methods distinguishable without bypassing other authorization checks.
- Warn and require confirmation if the browser already has a Folio session for a different User. Provide a legacy SSO button on Folio's login page. On expiry of Folio's one-hour session, save the active Form Draft and repeat the bridge if the old login remains valid; otherwise the old application handles login before returning to the Form.
- Read a required `roles: string[]` from the authenticated PDMS exchange. `admin (กปม.)` (case-insensitive, including `Admin` and `ADMIN`) maps to `admin`; otherwise the exact name `เจ้าหน้าที่ กปม.` maps to `viewer`; all other valid lists, including `[]`, map to `user`. Admin retains precedence when both names are present. Ignore letter case only for the full `admin (กปม.)` name; do not trim whitespace or match substrings to grant Admin. Missing, malformed or oversized claims fail SSO without changing roles. Keep the existing 8 KiB exchange response limit and timeout; never truncate roles to fit.
- Store nullable `Account.lastMappedRole` and `Account.lastSsoRoleGeneration`; retain no raw role list. A null baseline applies the current mapping on the first successful SSO, including existing links. Later logins preserve `User.role` when the mapping equals the baseline and replace it when the mapping changes. Manual Folio role edits change only `User.role`. This global role applies to both login methods. Mapping is observed only during SSO, so a change and reversal between logins is not detectable.
- Finalize the role, baseline, generation and session handoff atomically at direct login or confirmed account switch. Cancellation and expiry do not update role state. Existing account provisioning and approved binding may still precede confirmation, as before. Keep role evidence in the server-side challenge and bind it to the provider, subject, account and transaction; never trust browser-supplied roles. Serialize finalization and manual account edits with the same account lock. A later-started successfully completed SSO supersedes older transactions; advance the watermark even when roles are unchanged, and preserve the independent review cutoff.
- Revoke all older sessions and terminate their AI authoring when the effective role changes, not merely when the baseline changes. Preserve the last-enabled-Admin guard: reject a downgrade that would leave no enabled Admin, retaining the old role, baseline and watermark so a later attempt can retry. Keep manual role controls and this same guard. SSO bypasses only the local temporary-password-change requirement, including Admin account mutations; local password login still enforces it.
- Expose `session.isSso` to the web client so renewal follows the authentication method rather than role. Use `/admin`, `/admin/results` or `/dashboard` as the Admin, Viewer or User default respectively. Preserve validated destinations only when allowed for the resulting role: Viewers may return only to results list/detail pages, while Users cannot return to Admin pages. Preserve unsaved-work guards before switching or renewing. Do not merge this flow with the existing email-bound prefill handoff. Synchronizing logout or immediate old-system revocation is out of scope.

## Consequences

- Browser navigation must preserve only validated, local Form, dashboard or explicitly allowed Admin return paths. On success, the callback redirects to the configured `CORS_ORIGIN` web origin, not the API callback origin. The redirect origin comes only from server configuration, never request `Host`, forwarded headers, or user input. Failures return to the fixed login failure path on that same web origin. The callback must not expose the Folio session bearer in a redirect URL; current Folio API requests require a bearer token, so the browser session handoff needs a secure delivery path.
- Folio may implement its side first, but end-to-end verification requires PDMS Portal authorization and Auth issue/exchange APIs. The PDMS contract must supply a stable subject and authenticated stored email without asserting mailbox verification; no public self-registration, automatic email linking, or placeholder identity may silently replace this boundary. Controlled Folio verification does not establish live PDMS integration success.
- The existing prefill handoff still requires its own Folio login state and email match. SSO for a direct Form link does not remove that requirement.

## Required old-backend HTTP contract

Configure `LEGACY_SSO_AUTHORIZE_URL`, `LEGACY_SSO_EXCHANGE_URL`, `LEGACY_SSO_CALLBACK_URL`, `LEGACY_SSO_CLIENT_ID`, `LEGACY_SSO_CLIENT_SECRET`, and `LEGACY_SSO_PROVIDER_ID` together on Folio's server. The callback URL must be the exact public Folio API URI. `CORS_ORIGIN` identifies the trusted Folio web origin for redirects; direct local web development uses `http://localhost:5173`, while same-origin deployments use their public origin. Use HTTPS outside localhost and keep the client secret server-side.

The authorization bridge accepts a top-level GET with `client_id`, exact `redirect_uri`, unpredictable `state`, `code_challenge`, and `code_challenge_method=S256`. It authenticates the old User with the old application's existing login or refresh flow. It issues a cryptographically random, short-lived, single-use authorization code bound to client ID, exact callback URI, and PKCE challenge. Treat the code as opaque; Folio accepts standard Base64 characters such as `+`, `/`, and `=` and form-URL-encodes the exact value during exchange. The bridge redirects to the exact callback with only `code` and `state`; it never returns an access token or refresh token in the browser.

Folio redeems the code directly from its server using an HTTPS POST to the exchange URL. The request uses HTTP Basic authentication for the configured client ID and secret, plus form fields `grant_type=authorization_code`, `client_id`, `code`, `redirect_uri`, and `code_verifier`. The backend atomically rejects expired, replayed, unknown, or mismatched codes. It returns JSON with a stable, non-reassignable `sub`, the authenticated PDMS User's stored `email`, truthful `email_verified: false`, an optional `name`, and required `roles: string[]`. Roles are the current assigned names read inside the exchange transaction, excluding deleted roles and deleted assignments, ordered by role ID; no assignments yields `[]`. Do not reuse the browser token's role snapshot. Folio rejects missing or nonboolean `email_verified`, but accepts either boolean from the configured authenticated exchange; neither value changes a linked Folio profile. A name is optional provisioning data: Folio ignores nonstring, blank, unsafe, or over-limit values and uses the normalized email instead. Accepted names have no raw Unicode control characters and trim to at most 120 UTF-16 units. The backend does not return legacy access or refresh credentials. Neither side logs codes, credentials, or tokens.

Ticket 12 established the baseline for identities already mapped by `(providerId, accountId)` to an enabled `role=user` Folio account. First-time account provisioning and pending links were added in Tickets 13–14; account-switch confirmation and draft re-entry were added in Tickets 15–16. This PDMS alignment retains those guarantees while making completed mappings independent of email equality and retaining stale-transaction denial.

## Role-mapping rollout

Deploy the additive PDMS `roles` producer first; the previous Folio consumer ignores additional fields. Apply the additive nullable Folio migration and generate its Prisma client before deploying the role-aware consumer. Do not backfill the baseline from `User.role`, because that does not establish previous PDMS evidence. The first successful SSO applies the incoming mapping once and may replace a manual role selected before this update.

Validate with isolated databases and the existing SSO, account-management and editor regression suites. A producer rollback that removes `roles` makes new Folio SSO fail closed. An old Folio consumer rejects SSO Admins, so application rollback is not automatically compatible after promotion. Plan recovery and verify access before deployment; retain the additive columns during rollback.

## VIEWER amendment (27 October 2026)

The officer mapping grants results-only access instead of Admin authority. VIEWER reuses the existing Admin results list and detail pages to inspect all owners' saved Drafts, Submissions and Correction history, including document previews and available downloads. All Form/Response mutations, editor leases and editing capabilities, account/link administration, audit browsing and AI authoring remain unavailable to VIEWER. A read-only preview contains no write callback or editing capability. Existing Admin and User permissions remain unchanged.

Apply the additive `viewer` enum migration and regenerate Prisma before deploying the consumer. The previous officer baseline is `admin`, so the next successful officer SSO observes `admin -> viewer`, applies the downgrade and revokes older sessions. Do not infer PDMS assignments from the current Folio role or perform a bulk role backfill. Unchanged mapping/manual-override semantics remain intact. Both SSO and manual account controls must protect the last enabled Admin against every non-Admin role, including Viewer; an affected last Admin needs another enabled Admin before retrying.

The rollout changes Folio's consumer only; PDMS continues supplying its existing authenticated role names. Older application builds do not understand `viewer`, so rollback requires an explicit compatibility plan rather than deleting the enum or silently promoting Viewers.
